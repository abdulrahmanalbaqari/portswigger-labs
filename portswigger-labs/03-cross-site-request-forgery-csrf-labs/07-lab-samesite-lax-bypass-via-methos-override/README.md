## ملخص شامل: CSRF Bypass عن طريق SameSite=Lax و Method Override

### 1. أساس الحماية: SameSite=Lax إزاي بيشتغل

لما كوكي السيشن معمول عليه `SameSite=Lax`، المتصفح بيمنع إرسال الكوكي في أي طلب **cross-site** زي POST forms، fetch، XHR جاية من موقع تاني.

**الاستثناء الوحيد**: لو الطلب عبارة عن **top-level navigation بطريقة GET** (يعني اليوزر بيتنقل فعليًا لصفحة، زي ضغط لينك أو `<img src>` أو redirect) - في الحالة دي الكوكي **بيتبعت طبيعي** حتى لو جاي من موقع تاني.

### 2. ليه ده بيبقى ثغرة

المشكلة بتحصل لما:

- الديفلوبر يفترض إن **GET = آمن (safe)** ومفيهوش أي تغيير في الداتا، فبيستثنيه من فحص الـ CSRF token في الكود:

python

```python
if request.method == "GET":
    process_request()  # مفيش فحص CSRF
else:
    verify_csrf_token(request)
    process_request()
```

- وفي نفس الوقت، فيه endpoint حساس (حذف، تحويل فلوس، تغيير إيميل) بيتنفذ عن طريق GET

لو الحاجتين اتقابلوا مع بعض، المهاجم يقدر يعمل:

html

```html
<img src="https://target.com/delete-account?id=123">
```

المتصفح بيبعت الكوكي (لأنه Lax وده top-level-ish load)، ومفيش فحص CSRF أصلاً (لأنه GET)، فالعملية بتتنفذ.

### 3. ليه المفروض GET يفضل "Safe" أصلاً

مش بس علشان CSRF - ده مبدأ HTTP أساسي:

- GET المفروض بس **بيقرا**، مالوش side effects
- بيتعمله **prefetch تلقائي** من المتصفح من غير تفاعل حقيقي من اليوزر
- بيتخزن في الـ **history/logs/Referer** - تسريب معلومات
- وطبعًا، هو الحالة الوحيدة اللي الكوكي بيتبعت فيها cross-site مع Lax

### 4. معنى كلمة "Override" في السياق ده

"Override" هنا مش معناها إعداد بيتغير - هي وصف عام لـ **تخطي/إلغاء أثر الحماية**. يعني "SameSite Lax override" = الطريقة اللي بيها الحماية الافتراضية بتاعة Lax بتتلغى فعليًا، عن طريق استغلال إن GET requests مستثناة من القيود.

### 5. اللي انت لقيته فعليًا: HTTP Method Override Bypass

ده اكتشاف مختلف وأقوى من الحالة العادية. اللي حصل:

1. جربت تبعت GET بدل POST → السيرفر رفض بـ **405 Method Not Allowed** (لأن الـ route متسجل بس على POST في الفريموورك)
2. لما ضفت `_method=POST` (أو `X-HTTP-Method-Override: POST`) → الطلب اتقبل ونجح

**السبب**: فريمووركات زي Laravel وRails بتدعم تقنية اسمها **Method Override**، الأصل منها إنها تسمح لـ HTML forms (اللي مبتدعمش غير GET/POST) إنها "تحاكي" PUT/PATCH/DELETE.

**المشكلة الأمنية**: لو فحص الـ CSRF middleware بيشتغل على الـ **method الأصلي (GET)** قبل ما الفريموورك يعيد تفسيره كـ POST، يبقى:

- CSRF check شايف الطلب GET → **مفيش فحص**
- لكن الفريموورك جوه بينفذه فعليًا كـ **POST** (state-changing)

النتيجة: تقدر تعمل PoC حقيقي بـ HTML بسيط:

html

```html
<img src="https://target.com/delete-account?id=123&_method=POST">
```

ده يشتغل من متصفح حقيقي (مش بس من Burp)، الكوكي بيتبعت، مفيش CSRF check، والعملية بتتنفذ.

### 6. إزاي تتأكد إنه bypass حقيقي

- تأكد إن العملية فعلاً اتنفذت (الداتا اتغيرت في الـ DB)
- جرب من غير أي CSRF token خالص
- اعمل الطلب كـ HTML PoC فعلي (form/img) مش بس من أداة زي Burp، عشان تتأكد إنه exploitable في الواقع

### 7. الحل الصح (Remediation)

- الـ CSRF middleware لازم يتحقق من الـ method **بعد** إعادة التفسير (بعد الـ method override)، مش قبلها
- عدم استثناء GET من فحص CSRF لو فيه أي احتمال إنه يتحول لـ state-changing عن طريق override
- كل endpoint حساس يستخدم POST/PUT/DELETE فقط، ومفيش اعتماد على method override في العمليات الحساسة
- إضافة فحص `Origin`/`Referer` header كطبقة حماية إضافية
