الفكرة الأساسية: التطبيق بيحدد بيانات المستخدم (زي صفحة الحساب الشخصي) بناءً على قيمة `id` أو `user_id` بتتبعت في الـ request (سواء في الـ URL أو في الـ cookie)، من غير ما يتأكد إن الشخص اللي طالب الصفحة دي هو فعلاً صاحب الـ ID ده.

### الفرق عن اللاب "الأساسي" بتاع نفس الفئة

في النسخة الأبسط من اللاب ده (Lab: User ID controlled by request parameter)، الـ ID بيكون **رقم متسلسل بسيط** زي `1`, `2`, `3`... فتقدر تخمنه بسهولة وتجرب أرقام مختلفة.

لكن في النسخة دي (**with unpredictable user ID**)، الـ ID مش رقم بسيط — هو غالبًا **GUID/UUID** طويل وعشوائي، زي:

```
7b5f1cbb-0abb-4dd1-a020-70fc1cd14926
```

فمينفعش تخمنه أو تجرب أرقام متتالية زي `1, 2, 3`. الحماية هنا معتمدة على فكرة "**security through obscurity**" — يعني المطور افتكر إن طالما الـ ID صعب التخمين، يبقى النظام آمن، وده اعتقاد غلط.

### طريقة الاستغلال (الفكرة)

بما إن التخمين مش وارد، لازم تلاقي طريقة **تسرب (leak)** بيها الـ ID الخاص بمستخدم تاني من مكان تاني في التطبيق. الأماكن الشائعة اللي ممكن الـ ID يتسرب منها:

- في صفحة فيها **مراجعات منتجات (product reviews)** أو تعليقات، ولينك بروفايل كل يوزر فيها بيظهر GUID بتاعه.
- داخل الـ **HTML source code** أو الـ JSON response لصفحة معينة (زي صفحة تانية بتعرض بيانات مستخدمين تانيين بشكل غير مباشر).
- في **API endpoint** تاني بيرجع بيانات مستخدمين من غير قصد.

### خطوات الحل (النمط العام لهذا اللاب في PortSwigger)

1. **سجل دخول** بحسابك (`wiener:peter` غالبًا) وافتح صفحة "My account"، هتلاقي الـ URL شبه:

```
   /my-account?id=7b5f1cbb-0abb-4dd1-a020-70fc1cd14926
```

1. **دوّر في الموقع** على أي مكان بيظهر فيه مستخدمين تانيين — أشهر مكان في اللاب ده هو صفحة منتج فيها **قسم تقييمات/تعليقات (Reviews)** بواسطة مستخدمين تانيين.
2. **افحص الـ HTML source** بتاع الصفحة دي (View Page Source أو من خلال Burp) ودوّر جوه اللينكات، ممكن تلاقي لينك زي:

```
   <a href="/my-account?id=8e1e8f5c-2b39-4f9c-9b13-xxxxxxxx">carlos</a>
```

ده معناه إنك لقيت الـ GUID بتاع `carlos` (الأدمن/الضحية المستهدفة في معظم لابات PortSwigger).

1. **انسخ الـ GUID ده**، وروح استبدل بيه قيمة الـ `id` في الـ URL بتاعك:

```
   /my-account?id=8e1e8f5c-2b39-4f9c-9b13-xxxxxxxx
```

1. ابعت الريكوست (سواء من المتصفح مباشرة أو من Burp Repeater).
2. لو نجحت، هتشوف بيانات حساب `carlos` بدل حسابك، وده معناه إنك عديت الـ access control، واللاب هيتحل تلقائيًا.

### الدرس المستفاد

- الاعتماد على **صعوبة تخمين المعرف** (GUID عشوائي) مش بديل عن **access control حقيقي**. ده مبدأ اسمه *security through obscurity* وهو غير كافٍ كحماية وحيدة.
- لازم أي endpoint بيرجع بيانات حساسة لمستخدم معين، السيرفر **يتحقق من هوية الطالب نفسه** (من الـ session بتاعته) ويتأكد إنه هو صاحب الـ resource ده، مش يعتمد بس على القيمة اللي المستخدم بعتها.
- أي مكان في التطبيق بيسرب معرفات مستخدمين تانيين (حتى لو "غير مقصود" زي صفحة تعليقات) بيبقى نقطة ضعف تسهّل استغلال الثغرة دي.
