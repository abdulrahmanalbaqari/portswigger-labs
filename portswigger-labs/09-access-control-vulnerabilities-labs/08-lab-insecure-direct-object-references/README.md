اللاب ده مثال كلاسيكي على ثغرة **IDOR** (Insecure Direct Object Reference)، بس هنا التطبيق العنصر (object) اللي بيتم الوصول له مباشرة مش سجل في قاعدة بيانات، لكن **ملف فعلي على السيرفر** (static file) — وتحديدًا ملفات نصوص فيها **transcripts** (نسخ محادثات) بتاعة خدمة الـ Live Chat.

### طبيعة الثغرة

التطبيق فيه خاصية **Live chat** — لما تبعت رسالة وتضغط "View transcript"، بيديك رابط لملف نصي يحتوي على نسخة المحادثة، شكله تقريبًا:

```
GET /chat/71.txt
```

المشكلة:

1. الملفات دي بتتخزن على السيرفر بأسماء بسيطة عبارة عن **رقم متسلسل (incrementing number)** — يعني `1.txt`, `2.txt`, `3.txt`... إلخ.
2. **مفيش أي تحقق** إن الشخص اللي بيطلب الملف ده هو صاحب المحادثة الأصلية. أي حد يعرف اسم الملف (أو الرقم) يقدر يوصله مباشرة.
3. بما إن الأرقام متسلسلة وسهلة التخمين، تقدر تجرب أرقام تانية غير رقمك (زي `1.txt`, `2.txt`...) وتشوف محادثات مستخدمين تانيين، ومنهم `carlos`.

### خطوات الحل (زي الرسمي بالظبط)

1. **افتح اللاب** وروح لتبويب **Live chat**.
2. **ابعت أي رسالة** في الشات (أي نص عادي، مش مهم محتواها) عشان يتولد ليك transcript.
3. اضغط على **"View transcript"** — هيوديك على صفحة/ملف نصي برابط شبه:

```
   https://<lab-id>.web-security-academy.net/chat/72.txt
```

1. **لاحظ الـ URL** كويس: الاسم عبارة عن رقم (`72.txt` في المثال) + امتداد `.txt`. يبقى واضح إن ده **رقم متسلسل** بيتزود مع كل محادثة جديدة.
2. **غيّر الرقم** في الـ URL لرقم صغير زي `1.txt`:

```
   https://<lab-id>.web-security-academy.net/chat/1.txt
```

1. افتح الرابط الجديد، وهتلاقي محتوى محادثة قديمة (مش بتاعتك) — دي على الأرجح محادثة `carlos` مع الدعم، وجوه المحادثة دي ممكن تلاقيه ذكر **باسورده** بالغلط (زي لو نسي الباسورد وطلب من الدعم يفتحله الحساب أو حاجة شبه كده).
2. **انسخ الباسورد** ده.
3. ارجع لصفحة اللاب الرئيسية واعمل **Login** بـ:

```
   username: carlos
   password: <الباسورد اللي لقيته في الشات>
```

1. لو دخلت بنجاح، اللاب بيتحل تلقائيًا ✅.

- مفيش ربط بين **الـ session بتاعتك** وبين رقم الملف اللي بتطلبه.
- الأرقام **متسلسلة وسهلة التخمين** (مش UUID عشوائي)، فأي حد يقدر يعد من 1 لغاية آخر رقم ويشوف كل المحادثات.
- الملفات دي بتتخزن بشكل **static** (يعني أي حد وصله الرابط يقدر يفتحه من غير أي auth) بدل ما تتحفظ مرتبطة بحساب المستخدم وتتفحص صلاحياته وقت الطلب.

### الدرس المستفاد

- أي **معرف (identifier)** بيُستخدم للوصول لمورد حساس (ملف، سجل، صفحة) لازم يترافق مع **access control check حقيقي**، مش مجرد الاعتماد على إن الرابط "مش معروف" أو صعب لقايته.
- استخدام أرقام متسلسلة كأسماء ملفات أو IDs بيخلي الـ enumeration (تجربة كل الأرقام واحد واحد) سهل جدًا.
- تخزين بيانات حساسة (زي محادثات فيها معلومات شخصية أو باسوردات) كملفات static قابلة للوصول المباشر (direct static file access) من غير أي طبقة تحقق هو خطأ تصميمي خطير.
- **الحل الصحيح المفروض يكون**:
    - كل transcript يترابط بمعرف المستخدم (owner) في الـ database.
    - أي طلب لعرض transcript يتحقق إن الـ session الحالية بتخص نفس صاحب المحادثة.
    - استخدام معرفات غير قابلة للتخمين (UUID) كخط دفاع إضافي (مش بديل عن الـ access control، زي ما شفنا في لاب الـ unpredictable user ID قبل كده).
