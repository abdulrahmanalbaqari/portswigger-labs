### طبيعة الثغرة

النظام بيستخدم **Account locking**: لو حاولت تدخل على حساب معين بمعلومات غلط عدد معين من المرات (زي 3 أو 4)، الحساب ده بيتقفل مؤقتًا، وبيديك رسالة مختلفة زي:

```
You have made too many incorrect login attempts.
```

المشكلة (الـ Logic Flaw): **رسالة القفل دي بتظهر بس لو الـ username كان صحيح فعلاً وموجود في النظام**. لو جربت يوزرنيم مش موجود أصلاً، النظام هيرجعلك دايمًا نفس رسالة الخطأ العادية ("Invalid username or password")، **حتى لو كررتها كتير**، لأنه مفيش حساب حقيقي يتقفل من الأساس.

يعني الفرق في الرسالة (أو طول الـ response) بين:

- يوزرنيم **مش موجود** → رسالة عادية ثابتة، مهما كررت المحاولات.
- يوزرنيم **موجود فعلاً** → بعد كذا محاولة، الرسالة بتتغير لرسالة "الحساب اتقفل" — وده بيفضح إن اليوزرنيم ده حقيقي.

هنا بقى عندنا **side channel** (قناة جانبية) بتسرّب معلومة (هل اليوزرنيم موجود ولا لأ) من غير ما تقصد فعلاً.

### خطوات الحل بالتفصيل (باستخدام Burp Intruder)

#### المرحلة 1: اكتشاف اليوزرنيم الصحيح (Username Enumeration)

1. **ابعت محاولة تسجيل دخول غلط** (username وباسورد وهميين)، وابعت الريكوست على **Burp Intruder**:

```
POST /login HTTP/1.1
...
username=invalid-username&password=example
```

1. اختار نوع الهجوم **Cluster bomb** (بيجرب كل تركيبة ممكنة بين المتغيرين، مش زي الـ Pitchfork اللي بيمشي بالتوازي).
2. حط **Payload position** على قيمة الـ `username`، وضيف **payload position فاضية** كمان في آخر الـ body:

```
username=§invalid-username§&password=example§§
```

الفكرة من الـ position الفاضية دي: هنستخدمها بس عشان **نكرر كل يوزرنيم عدة مرات** (5 مرات في الحالة دي)، من غير ما تغيّر حاجة فعلية في الريكوست.

1. في **Payloads panel**:
    - **Position 1** (اليوزرنيم): حط قائمة الـ **candidate usernames**.
    - **Position 2** (الفاضية): اختار نوع **Null payloads**، واختار توليد **5 payloads**. ده هيخلي كل يوزرنيم يتكرر **5 مرات متتالية** (5 محاولات فاشلة لكل يوزرنيم، عشان تتخطى حد القفل المفترض لو اليوزرنيم ده حقيقي).
2. **شغّل الهجوم (Start attack)**.
3. **افحص النتائج**: هتلاقي إن أغلب اليوزرنيمات بترجع responses بنفس الطول تقريبًا (رسالة الخطأ العادية)، **إلا يوزرنيم واحد** بترجع responses أطول (أو مختلفة)، وفيها رسالة زي:

```
You have made too many incorrect login attempts.
```

ده معناه إن اليوزرنيم ده **موجود فعلاً**، ولأنه اتكرر 5 مرات غلط، الحساب اتقفل، فظهرت رسالة القفل بدل رسالة الخطأ العادية.

1. **سجّل اليوزرنيم ده** (خليه نسميه بس مثال `X`).

#### المرحلة 2: تخمين الباسورد الصحيح (Brute-force)

1. اعمل هجوم Intruder **جديد** على نفس الـ `POST /login`، بس المرادي:
    - اختار نوع الهجوم **Sniper** (بيجرب متغير واحد بس، والباقي ثابت).
    - ثبّت قيمة `username` على اليوزرنيم اللي اكتشفته.
    - حط **Payload position** بس على الـ `password`.
2. ضيف **قائمة candidate passwords** كـ payload set.
3. اعمل **Grep - Extract rule** يستخرج رسالة الخطأ من كل response (عشان تقدر تقارن بسهولة).
4. **شغّل الهجوم**.
5. **افحص عمود الـ Grep extract**: هتلاقي أغلب المحاولات فيها رسالة خطأ (إما "Invalid credentials" أو "account locked" لو الحساب كان لسه مقفول من التجربة اللي فاتت)، **إلا محاولة واحدة معندهاش أي رسالة خطأ خالص** — دي علامة إن تسجيل الدخول **نجح** فعليًا (يعني رجع redirect بدل رسالة خطأ).
6. **سجّل الباسورد** المقابل للمحاولة دي.

#### المرحلة 3: تسجيل الدخول الفعلي

1. بما إن الحساب غالبًا لسه **مقفول مؤقتًا** بسبب كل المحاولات اللي عملتها، **استنى دقيقة (أو الوقت المحدد لفك القفل)**.
2. بعد ما ينفك القفل، سجّل دخول بـ:

```
username: <اليوزرنيم اللي اكتشفته>
password: <الباسورد اللي اكتشفته>
```

1. افتح صفحة الحساب، واللاب هيتحل تلقائيًا ✅.

### ليه ده بيحصل تقنيًا

الكود بيكون شبه كده:

python

```python
def login(username, password):    if not user_exists(username):        return "Invalid username or password", 200   # رسالة موحدة لغير الموجودين    if is_locked(username):        return "You have made too many incorrect login attempts.", 200  # ❌ رسالة مختلفة تمامًا    if not check_password(username, password):        increment_failed_attempts(username)        return "Invalid username or password", 200    return "Login successful", 302
```

المشكلة: **الفرع اللي بيتحقق من `is_locked()` بيتنفذ بس لو اليوزر موجود أصلاً** (لأن مينفعش تقفل حساب مش موجود). فوجود رسالة القفل نفسها هو **دليل غير مباشر (indirect signal)** على وجود الحساب، حتى لو مفيش أي رسالة صريحة بتقول "اليوزرنيم صح".

### الدرس المستفاد

- **أي فرق ملحوظ في سلوك السيرفر** (رسالة مختلفة، طول response مختلف، زمن استجابة مختلف) بناءً على وجود اليوزرنيم من عدمه هو **ثغرة username enumeration**، حتى لو الرسائل الأساسية بتبان موحدة ظاهريًا.
- آليات الحماية الإضافية (زي Account locking) لازم تُصمم بحرص شديد عشان **متضيفش قناة تسريب معلومات جديدة (side channel)** — فالحماية نفسها بقت أداة استكشاف للمهاجم.
- الحل الصحيح: **رسالة القفل والرسالة العادية للباسورد الغلط لازم تكون موحدة تمامًا** بغض النظر عن حالة الحساب الداخلية (موجود/مش موجود/مقفول)، وأي فحص لحالة القفل لازم يحصل **بعد** ما ترجع نفس نوع الرسالة العامة، مش قبلها.
- استخدام **Null payloads** في Burp Intruder تكنيك مفيد لما تحتاج "تكرر" قيمة معينة عدد مرات ثابت من غير ما تضيف تغيير حقيقي في الريكوست.
- **Grep - Extract** في Intruder أداة قوية جدًا لمقارنة نتائج كتير بسرعة من غير ما تفحص كل response لوحده يدويًا.
