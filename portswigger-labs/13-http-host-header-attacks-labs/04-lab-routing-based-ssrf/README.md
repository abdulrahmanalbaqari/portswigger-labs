- الفكره من الLab ده

```bash
1. Host: 192.168.0.11

2. POST /admin/delete HTTP/2
Host: 192.168.0.11
csrf=D1t3Gif1fzpByE1DnfM8wBMEHoH04Nho&username=carlos
```

### 

اللاب ده من فئة **SSRF (Server-Side Request Forgery)**، وتحديدًا نوع متقدم اسمه **Routing-based SSRF**. الفكرة الأساسية مختلفة عن الـ SSRF "الكلاسيكي" (اللي بيكون فيه parameter صريح زي `?url=http://...`) — هنا **مفيش أي حقل واضح بيقبل URL**. بدل كده، الثغرة موجودة في **هيدر `Host`** نفسه، والاستغلال بيحصل على مستوى **بنية الشبكة الداخلية (internal network routing)**.

### طبيعة الثغرة (السياق المعماري)

الموقع مبني بمعمارية من طبقتين:

```
[Client] → [Front-end / Load Balancer / Middleware] → [Back-end application servers]
```

الـ **middleware** (الطبقة الوسيطة) بيستخدم قيمة هيدر **`Host`** الجاية من العميل عشان **يقرر لأي سيرفر داخلي يوجّه الطلب**. يعني بدل ما يكون عنده IP ثابت للـ back-end، بيثق في الـ `Host` header ويستخدمه كجزء من عملية الـ **routing الداخلي**.

المشكلة: بما إن الـ **middleware بيقدر يوصل لأي عنوان IP داخلي** (لأنه جزء من الشبكة الداخلية نفسها)، لو قدرت **تتحكم في قيمة الـ Host header بحرية**، تقدر **تجبر الـ middleware إنه يبعت الطلب لأي IP داخلي تختاره انت** — بما فيها عناوين مش المفروض تكون متاحة للعامة، زي لوحة تحكم إدارية داخلية (`192.168.0.0/24`).

### خطوات الحل بالتفصيل

#### المرحلة 1: التأكد إن الـ Host Header بيتحكم في الـ Routing (باستخدام Burp Collaborator)

بما إن firewall الأكاديمية بيمنع أي تفاعل مباشر مع سيرفرات خارجية عشان تحمي أطراف تالتة، لازم نستخدم **Burp Collaborator's default public server** كأداة "استماع" آمنة نتأكد بيها إن الطلب فعلاً بيتبعت لمكان بنحدده احنا.

1. ابعت الـ `GET /` (اللي بيرجع `200 OK`) على **Burp Repeater**.
2. حدد قيمة الـ **`Host` header**، كليك يمين واختار:

```
   Insert Collaborator payload
```

ده هيستبدل القيمة بدومين خاص بتاع Collaborator (زي `xxxxx.oastify.com`).

3. ابعت الريكوست.

4. روح لتبويب **Collaborator**، ودوس **"Poll now"**. لو شفت **تفاعلات شبكة (network interactions)** — خصوصًا طلب HTTP — يبقى تأكدنا إن **الـ middleware فعلاً بيعمل طلب خارجي لأي domain نحطه في الـ Host header**. ده الدليل القاطع إن SSRF موجودة.

#### المرحلة 2: مسح الشبكة الداخلية (Internal Network Scanning) باستخدام Burp Intruder

بما إن عرفنا إن الـ Host header بيتحكم في الـ routing، الخطوة الجاية هي **اكتشاف عنوان IP الداخلي** بتاع لوحة التحكم الإدارية، من خلال تجربة كل الاحتمالات في range `192.168.0.0/24`.

1. ابعت نفس الـ `GET /` request على **Burp Intruder**.
2. في إعدادات Intruder، **شيل تفعيل "Update Host header to match target"** — عشان Burp ميرجعش يصلّح الـ Host header تلقائيًا لقيمة الموقع الأصلي (لأننا عايزينه يفضل بالقيمة اللي إحنا حاططينها).
3. غيّر قيمة الـ Host header لـ:

```
   Host: 192.168.0.§0§
```

وحط **payload position** على آخر رقم (الـ octet الأخير) بس.

4. في **Payloads panel**، اختار نوع **"Numbers"**:

- From: `0`
- To: `255`
- Step: `1`

ده هيولد كل عناوين IP من `192.168.0.0` لـ `192.168.0.255`.

5. دوس **Start attack**. هيظهرلك تحذير إن الـ Host header مش مطابق للـ target host — **تجاهله**، ده متوقع وطبيعي لأننا بنعمله عمدًا.

#### المرحلة 3: تحليل النتائج وتحديد اللوحة الإدارية

1. لما الهجوم يخلص، رتّب النتائج حسب عمود **Status**. هتلاقي **response واحد بس** رجع **`302`** (Redirect) لصفحة `/admin` — بينما باقي الـ IPs رجعوا إما `200` عادي أو أخطاء تانية.
ده معناه إن الـ IP ده تحديدًا (اللي جاب الـ 302) هو **عنوان السيرفر الداخلي اللي فيه لوحة التحكم الإدارية**، وده لأن السيرفر ده بيعمل redirect تلقائي لـ `/admin` (غالبًا لأن الصفحة الرئيسية بتوجهك مباشرة لصفحة تسجيل الدخول الإدارية).
2. ابعت الريكوست ده (اللي جاب الـ 302) على **Burp Repeater**.

#### المرحلة 4: الوصول الفعلي للوحة التحكم

1. في Repeater، غيّر الـ request line لـ:

```
   GET /admin
```

(مع الحفاظ على نفس الـ Host header بتاع الـ IP الداخلي المكتشف). ابعت الريكوست.

9. في الـ response، هتلاقي إنك **دخلت فعليًا للوحة التحكم الإدارية** — بدون أي authentication، لأن اللوحة دي "غير آمنة (insecure)" ومصممة أصلاً على افتراض إن محدش غير الموظفين الداخليين يقدر يوصلها (لأنها على IP داخلي مش متاح من الإنترنت أصلاً) — وده بالظبط اللي كسرناه بالـ SSRF.

#### المرحلة 5: حذف carlos (بناء الريكوست يدويًا)

1. ادرس فورم حذف المستخدمين في الصفحة، هتلاحظ إنه بيولّد طلب:

2. كليك يمين على الريكوست واختار **"Change request method"** — Burp هيحوّله تلقائيًا لـ:

المشكلة الجوهرية: الـ **middleware بيثق في الـ Host header** بشكل كامل عشان يحدد **وجهة الطلب داخل الشبكة الداخلية نفسها**، وبما إن الـ middleware **جزء من الشبكة الداخلية أصلاً** وعنده صلاحية وصول لكل عناوين `192.168.0.0/24`، فأنت بتستخدمه **كوكيل (proxy) غير مقصود** يوديك لأي مكان داخلي تحبه، حتى لو انت نفسك (كمستخدم خارجي) مش المفروض توصل للشبكة الداخلية دي أبدًا.

### الدرس المستفاد

- **الـ Host header لازم يتفحص ويتحقق منه بصرامة**، ومينفعش يُستخدم مباشرة لاتخاذ قرارات routing داخلية بدون **whitelist صارم** لقيم مسموح بيها فقط.
- **SSRF مش دايمًا شكلها "واضح" زي `?url=`** — أي مكان في التطبيق بيقدر يخلي السيرفر "يزور" مكان تاني بناءً على مُدخل تتحكم فيه انت (حتى لو ده هيدر HTTP عادي زي Host) هو سطح هجوم SSRF محتمل.
- **Burp Collaborator** أداة أساسية جدًا لاكتشاف SSRF "أعمى (blind)" — يعني حالات مفيش فيها أي رد فعل ظاهر في الـ response نفسه يأكد الثغرة، فبتحتاج قناة خارجية (out-of-band) تتأكد بيها إن الطلب فعلاً حصل.
- **Burp Intruder بأنواع الـ Payload زي "Numbers"** أداة قوية جدًا لعمل **مسح شامل لمساحة عناوين IP داخلية (internal IP range scanning)** بسرعة، وده تكنيك أساسي في أي اختبار SSRF حقيقي.
- **أي نظام "داخلي فقط" (internal-only)** لازم **معتمدش على "عدم الوصول من الإنترنت" كوسيلة أمان وحيدة** — لازم يكون عنده **authentication حقيقي بغض النظر عن مصدر الطلب**، لأن أي SSRF في أي مكون تاني في الشبكة ممكن يفتح الباب للوصول له.
