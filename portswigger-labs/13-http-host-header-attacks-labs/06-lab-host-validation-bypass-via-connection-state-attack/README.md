اللاب ده من أعقد وأحدث لابات الـ **Host Header/SSRF**، ومبني على بحث حديث من PortSwigger Research اسمه **"Browser-Powered Desync Attacks"**. الثغرة هنا **مختلفة جوهريًا** عن اللابين اللي فاتوا — مش مشكلة في **تحليل (parsing) الريكوست نفسه**، لكن مشكلة في **إدارة حالة الاتصال (Connection State)** بين طلبات متعددة على نفس الـ TCP connection.

### المفهوم الأساسي: HTTP Connection Reuse (Keep-Alive)

في HTTP الحديث، المتصفح (أو أي عميل) بيفتح **اتصال TCP واحد** ويقدر **يبعت عليه أكتر من request متتالي** (بدل ما يفتح اتصال جديد لكل طلب) — ده بيُعرف بـ **"Keep-Alive"** أو **"Connection persistence"**، وبيحسّن الأداء بشكل كبير.

### طبيعة الثغرة (الـ Logic Flaw في الـ Front-end)

الموقع فيه **front-end server** (زي reverse proxy) بيعمل **فحص صارم وقوي على الـ Host header** — يبان إنه محمي كويس جدًا. المشكلة إن الفحص ده بيحصل **بشكل خاطئ من ناحية التوقيت**:

> **الـ front-end بيفحص الـ Host header بس في أول طلب (first request) على الاتصال، وبعدين بيفترض إن كل الطلبات اللي جايه بعد كده على نفس الاتصال (نفس TCP connection) "موثوقة" تلقائيًا من غير ما يعيد الفحص عليهم.**
> 

يعني لو بعتّ **أول طلب** بـ Host header ضار (زي `192.168.0.1`)، الفحص هيرفضه ويردك على الصفحة الرئيسية. لكن لو بعتّ **طلب أول عادي وسليم** (يعدي الفحص بنجاح)، وبعدين بعتّ **طلب تاني بـ Host مختلف (ضار) على نفس الاتصال بالظبط**، الـ front-end **مش هيعيد الفحص على الطلب التاني** — لأنه بيفترض إن الاتصال كله "اتوثّق" من أول طلب.

### خطوات الحل بالتفصيل

#### 1. تأكيد الفحص الأساسي (وإنه بيمنع الوصول المباشر)

ابعت `GET /` على **Burp Repeater**، وعدّل:

- المسار لـ `/admin`.
- الـ **Host header** لـ `192.168.0.1`.

ابعت الطلب. هتلاقي إنك بترجعلك **الصفحة الرئيسية العادية** (redirect) — يعني الفحص الأمني عدى الطلب ورفضه بنجاح، ومحدش سمحلك تدخل الأدمن بانل مباشرة.

#### 2. جهّز مجموعة (Group) من طلبين في نفس الاتصال

1. **كرر (Duplicate)** التاب اللي فيه الطلب ده.
2. ضيف **التابين مع بعض في Group واحدة** (خاصية في Burp Repeater بتخلي أكتر من طلب يتبعتوا مع بعض على نفس الاتصال).

#### 3. جهّز الطلب الأول: طلب "بريء" يعدي الفحص

في **التاب الأول**:

- رجّع المسار لـ `/`.
- رجّع الـ Host header لقيمة اللاب الصحيحة:

```
  Host: YOUR-LAB-ID.h1-web-security-academy.net
```

#### 4. اضبط وضع الإرسال ليتبعتوا على نفس الاتصال (Single Connection)

من القائمة المنسدلة جنب زرار **Send**، اختار:

```
Send group in sequence (single connection)
```

ده مهم جدًا لأنه بيضمن إن الطلبين هيروحوا **على نفس TCP connection بالظبط** (مش اتصالين منفصلين)، وده أساس الاستغلال كله.

#### 5. تأكد من هيدر Connection

غيّر هيدر **`Connection`** لـ:

```
Connection: keep-alive
```

عشان تضمن إن الاتصال هيفضل مفتوح بعد أول طلب، مستعد لاستقبال الطلب التاني على نفسه.

#### 6. ابعت المجموعة وافحص النتائج

دوس Send، وراقب الردود:

- **الطلب الأول** (`GET /` بـ Host صحيح): هيرجع عادي، بيعدي الفحص.
- **الطلب التاني** (`GET /admin` بـ `Host: 192.168.0.1`): **هيرجع محتوى صفحة الأدمن بانل فعليًا!** لأن الـ front-end **افترض غلط إن الاتصال كله موثوق** بمجرد ما الطلب الأول عدى الفحص.

#### 7. ادرس فورم حذف المستخدمين

في الـ response بتاع صفحة الأدمن، هتلاقي فورم HTML بيوضح:

- الـ `action`: `/admin/delete`
- اسم الـ input: `username`
- قيمة الـ **CSRF token**.

#### 8. جهّز الطلب الثاني ليكون POST لحذف carlos

في **التاب الثاني** من المجموعة، غيّره ليبقى:

```
POST /admin/delete HTTP/1.1
Host: 192.168.0.1
Cookie: _lab=YOUR-LAB-COOKIE; session=YOUR-SESSION-COOKIE
Content-Type: application/x-www-form-urlencoded
Content-Length: <CORRECT>

csrf=YOUR-CSRF-TOKEN&username=carlos
```

**ملحوظة مهمة**: لازم تحسب الـ `Content-Length` صح (طول الـ body بالبايت)، وتاخد الـ CSRF token والـ session cookie من الـ response بتاع الطلب اللي فات (خطوة 6).

#### 9. ابعت التسلسل (Sequence) تاني

ابعت المجموعة (نفس أسلوب "Send group in sequence (single connection)")، وهتلاقي إن الطلب الأول بيعدي الفحص عادي، والطلب التاني (POST لحذف carlos) **بيتنفذ فعليًا على السيرفر الداخلي** (192.168.0.1) بسبب نفس ثغرة "الثقة في حالة الاتصال".

بمجرد ما `carlos` يتحذف، اللاب هيتحل تلقائيًا ✅.

### ليه ده بيحصل تقنيًا

python

```python
class FrontendProxy:    def __init__(self):        self.connection_validated = False   # ❌ متغير على مستوى الاتصال، مش الطلب    def handle_request(self, request, connection):        if not self.connection_validated:            if not is_valid_host(request.headers.get("Host")):                return "Forbidden", 403            self.connection_validated = True   # ❌ بيتحدد مرة واحدة بس لكل الاتصال        # باقي الطلبات على نفس الاتصال بتعدي من غير إعادة فحص!        return forward_to_backend(request)
```

المشكلة الجوهرية: **الفحص الأمني بيُطبّق على مستوى "الاتصال (Connection)" بدل ما يُطبّق على مستوى "كل طلب (Request) على حدة"**. ده افتراض خاطئ لأن **اتصال TCP واحد ممكن يحمل أكتر من طلب HTTP مختلف تمامًا** (زي ما شفنا هنا: أول طلب "بريء" وطلب تاني "ضار")، والفحص لازم يتكرر **لكل طلب لوحده**، مش يعتمد على نتيجة الطلب اللي قبله.

### العلاقة بمفهوم "Desync Attacks" (من البحث المذكور)

اللاب ده مبني على فئة أوسع من الهجمات اسمها **"Browser-Powered Desync Attacks"** — والفكرة العامة فيها إن **الـ front-end والـ back-end (أو أي طبقتين وسيطتين) بيختلفوا في فهمهم لحدود الطلبات (request boundaries) على نفس الاتصال**، وده بيخلي طلب من مستخدم يتفسر أو يتعامل معاه بشكل غلط بسبب طلب سبقه على نفس الـ connection — ده بيفتح الباب لهجمات زي **HTTP Request Smuggling** أيضًا، اللي هي فئة قريبة جدًا من المفهوم ده.

### الدرس المستفاد

- **أي حالة أمنية (state) لازم تُفحص لكل طلب على حدة**، مش يُفترض إنها "موروثة" من طلب سابق على نفس الاتصال — الثقة في اتصال TCP معينة **مش نفس الثقة في هوية أو صلاحية طلب معين**.
- **Connection reuse (Keep-Alive)** خاصية أداء مهمة جدًا، لكنها بتفتح فئة كاملة من الثغرات لو التطبيقات مبنية على **افتراضات خاطئة** عن تسلسل الطلبات على نفس الاتصال.
- **Burp Suite's "Send group in sequence (single connection)"** ميزة حديثة نسبيًا (من إصدار 2022.8.1) وأساسية جدًا لاختبار هجمات من النوع ده، لأنها بتضمن التحكم الدقيق في **ترتيب الطلبات على نفس الاتصال بالظبط**، وهو شيء صعب تتحكم فيه بأدوات تانية عادية.
- ده مثال على **فئة هجمات جديدة نسبيًا ومتطورة (Desync Attacks)** بتتطلب فهم عميق لتفاصيل بروتوكول HTTP على مستوى منخفض (low-level)، مش بس منطق التطبيق العادي.
