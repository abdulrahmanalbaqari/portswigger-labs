اللاب ده من فئة **OAuth Vulnerabilities**، وتحديدًا استغلال ضعف في تطبيق **OAuth Implicit Flow**. المشكلة الأساسية: **التطبيق العميل (Client Application - بمعنى موقع المدونة اللي بيستخدم OAuth للتسجيل)** بيثق **بشكل أعمى في بيانات المستخدم اللي بيستقبلها**، من غير ما يتحقق فعليًا إنها **مرتبطة حقًا بالـ access token** اللي جاله من خدمة الـ OAuth.

### مفهوم أساسي: إيه هو OAuth وإزاي بيشتغل هنا؟

**OAuth** بروتوكول بيسمح للمستخدم إنه يسجل دخول في موقع (Client App) باستخدام حسابه في خدمة تانية (زي فيسبوك أو جوجل — هنا "social media account" وهمي في اللاب). الفكرة العامة:

```
[User] → [Client App: "سجل دخول بحساب السوشيال ميديا"]
       → [OAuth Service: تسجيل دخول + موافقة]
       → [OAuth Service يرجّع بيانات المستخدم/token للـ Client App]
       → [Client App يسجّل المستخدم دخول بناءً على البيانات دي]
```

### طبيعة الثغرة تحديدًا هنا

بعد ما تسجل دخول عن طريق خدمة الـ OAuth، الموقع (Client App) بيستقبل **معلومات أساسية عن المستخدم** (زي الإيميل)، وبعدين بيبعت طلب **`POST /authenticate`** لنفسه، فيه:

- **الـ access token** (اللي المفروض يثبت هوية المستخدم).
- **معلومات المستخدم نفسها** (زي الإيميل) — **كـ parameters منفصلة**، مش مُستخرجة من الـ token مباشرة على السيرفر.

المشكلة الجوهرية: **الـ endpoint `/authenticate` بيثق في قيمة الإيميل اللي جاية في الـ request body، من غير ما يتحقق إنها فعلاً مطابقة للإيميل المرتبط بالـ access token على مستوى OAuth service نفسها**. يعني تقدر **تسجل دخول بحسابك الحقيقي** (وتاخد token صحيح)، وبعدين **تغيّر قيمة الإيميل يدويًا** في الطلب النهائي لإيميل حد تاني — والسيرفر **هيصدقك ويسجلك دخول بحساب الشخص التاني ده**.

### خطوات الحل بالتفصيل

#### 1. اعمل عملية OAuth Login العادية

وانت شغّل Burp Proxy، دوس **"My account"**، واكمل عملية تسجيل الدخول عن طريق OAuth (بحسابك `wiener:peter`). بعد ما تخلص، هتترجع لموقع المدونة وانت مسجل دخول.

#### 2. ادرس الـ OAuth Flow كامل في Burp

روح لـ **Proxy > HTTP history**، وتابع كل الطلبات من أول:

```
GET /auth?client_id=[...]
```

ده أول طلب في عملية الـ **authorization**، وبعده هتلاقي سلسلة طلبات بتمثل باقي عملية الـ OAuth.

#### 3. لاحظ الطلب الحاسم: POST /authenticate

هتلاحظ إن التطبيق (موقع المدونة) بيستقبل **معلومات أساسية عن المستخدم** من خدمة الـ OAuth (زي الإيميل)، وبعدين بيبعت طلب:

```
POST /authenticate
```

فيه:

- الـ **access token**.
- **معلومات المستخدم** (زي الإيميل) — **كـ parameter منفصل في نفس الطلب**.

#### 4. تلاعب في الإيميل داخل الطلب

ابعت الـ `POST /authenticate` على **Burp Repeater**. غيّر قيمة الإيميل لـ:

```
carlos@carlos-montoya.net
```

ابعت الطلب. لاحظ إن **مفيش أي خطأ** بيرجع — يعني السيرفر **قبل التعديل من غير أي اعتراض**، رغم إن الـ access token اللي انت بعته لسه بتاعك انت (`wiener`)، مش بتاع `carlos`.

#### 5. افتح النتيجة في المتصفح بنفس الجلسة

كليك يمين على الـ `POST` request في Repeater، واختار:

```
Request in browser → In original session
```

ده هيديك رابط، افتحه في المتصفح. هتلاقي نفسك **مسجل دخول فعليًا بحساب carlos**!

### ليه ده بيحصل تقنيًا

الكود بيكون شبه كده على جانب الـ **Client Application**:

python

```python
@app.route("/authenticate", methods=["POST"])def authenticate():    access_token = request.form.get("access_token")    email = request.form.get("email")   # ❌ بياخد الإيميل من الطلب نفسه، مش من الـ OAuth service    # ❌ مفيش أي تحقق إن الإيميل ده فعلاً مرتبط بالـ access_token ده!    user = find_user_by_email(email)    login_user(user)    return redirect("/my-account")
```

المشكلة الجوهرية: **الـ Client App كان المفروض يستخدم الـ access token عشان يستعلم مباشرة من خدمة الـ OAuth** (عن طريق endpoint زي `/user_info` أو `/me`) ويجيب بيانات المستخدم **الحقيقية المرتبطة بالـ token ده تحديدًا** من مصدر موثوق (خدمة الـ OAuth نفسها). بدل كده، التطبيق **اكتفى بأخذ بيانات المستخدم كـ parameter عادي في الطلب النهائي**، وده خلى المهاجم **يقدر يستبدل البيانات دي بأي قيمة يحبها**، طالما الـ access token نفسه صحيح (وبيعتبر "دليل كافٍ على إن العملية شرعية") رغم إنه مش مرتبط أصلاً بالهوية المزوّرة اللي انت حاططها.

### نقطة مهمة: ليه الـ Access Token "مايهمش" هنا؟

الثغرة موجودة تحديدًا لأن الـ **Client App بيتحقق من "وجود" access token صحيح**، لكن **مش بيتحقق من "تطابق" البيانات المرسلة (الإيميل) مع صاحب الـ token ده فعليًا**. يعني الـ token بيثبت "انت شخص مسجل دخول بطريقة شرعية عبر OAuth"، لكن مش بيثبت "الإيميل اللي بتقوله ده هو إيميلك الحقيقي".

### الدرس المستفاد

- **أي بيانات هوية (زي الإيميل) لازم تُستخرج مباشرة من خدمة الـ OAuth على السيرفر (Server-to-server call)**، باستخدام الـ access token، **مش تُقبل كـ parameter منفصل من العميل** — لأن العميل (المتصفح) نقطة غير موثوقة ويقدر يعدّل أي قيمة فيها.
- **الـ access token لوحده مش كافي كدليل هوية** — لازم يُستخدم فعليًا **للاستعلام عن الهوية الحقيقية المرتبطة بيه**، مش بس "يتأكد إنه موجود وصالح" بينما البيانات المصاحبة له بتتقبل من مصدر تاني غير موثوق.
- ده مثال كلاسيكي على **"Trusting client-supplied data over server-verified data"** — نفس الفكرة اللي شفناها في لابات كتير قبل كده (زي الـ IDOR، الـ hidden username field في تغيير الباسورد)، لكن هنا في سياق **بروتوكول OAuth** بالذات.
- تطبيقات الـ **OAuth Client لازم تتبع الـ best practices بدقة** — تحديدًا: التحقق من الـ token عن طريق استدعاء الـ OAuth provider نفسه (مش الوثوق ببيانات جانبية)، والتحقق من الـ `state` parameter (لمنع CSRF)، والتحقق من `aud` (audience) في التوكنات من نوع JWT لو مستخدمة.
