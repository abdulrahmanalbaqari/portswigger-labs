# Lab : SSRF via OpenID dynamic client registration

https://portswigger.net/web-security/oauth/openid/lab-oauth-ssrf-via-openid-dynamic-client-registration

- الفكره من الLab ده

```bash
1. GET /.well-known/openid-configuration HTTP/2
```

اللاب ده بيجمع بين **OAuth/OpenID Connect** و **SSRF**، وتحديدًا استغلال خاصية **Dynamic Client Registration** — وهي خاصية في معيار **OpenID Connect** بتسمح لأي تطبيق (Client App) إنه **يسجل نفسه تلقائيًا** مع خدمة الـ OAuth من غير تدخل يدوي من مسؤول الخدمة.

### المفهوم الأساسي: Dynamic Client Registration

في الوضع العادي، لما تطبيق عايز يستخدم OAuth، مطوره بيروح يسجل التطبيق يدويًا عند مزوّد الخدمة (زي Google/Facebook Developer Console) ويحصل على `client_id` و`client_secret`.

**Dynamic Client Registration** (معرّف في **RFC 7591**) بتسمح لأي تطبيق إنه **يسجل نفسه تلقائيًا عن طريق API endpoint مخصص**، من غير أي مصادقة مسبقة — ده مفيد لسيناريوهات معينة، لكنه **خطير جدًا لو مش محكوم بقيود صارمة**، لأنه بيدّي **أي حد غريب** (بما فيهم مهاجم) القدرة على "يسجل تطبيق وهمي" ويتحكم في بعض البيانات المرتبطة بيه.

### طبيعة الثغرة

من بين البيانات اللي بتُقبل وقت التسجيل، فيه خاصية اسمها **`logo_uri`** — بتسمح للتطبيق إنه يحدد **رابط للوجو بتاعه**، واللي هيتعرض لاحقًا في صفحة "Authorize" (صفحة الموافقة اللي بتظهر للمستخدم وقت تسجيل الدخول عبر OAuth).

المشكلة: **خدمة الـ OAuth نفسها بتعمل طلب HTTP لجلب الصورة من الـ `logo_uri` ده** — وبما إن القيمة دي **بتتحدد بالكامل من التطبيق المسجّل (يعني من المهاجم)**، ده بيفتح **SSRF كامل**: تقدر تخلي خدمة الـ OAuth (اللي غالبًا شغالة على سيرفر cloud، زي AWS) **تعمل طلب لأي URL تحدده انت**، بما فيها عناوين داخلية حساسة زي **الـ AWS metadata endpoint**:

```
http://169.254.169.254/latest/meta-data/iam/security-credentials/admin/
```

#### إيه هو الـ AWS Metadata Endpoint (169.254.169.254)؟

ده عنوان IP خاص **متاح فقط من داخل أي instance شغالة على AWS EC2**، وبيديك معلومات عن الـ instance نفسها — من ضمنها **بيانات اعتماد مؤقتة (temporary credentials)** لأي IAM Role مرتبط بالـ instance. لو قدرت توصله عن طريق SSRF، تقدر **تسرق مفاتيح الوصول السحابية بالكامل**.

### خطوات الحل بالتفصيل

#### 1. افحص إعدادات OpenID الخاصة بالسيرفر

افتح:

```
https://oauth-YOUR-OAUTH-SERVER.oauth-server.net/.well-known/openid-configuration
```

ده ملف إعدادات قياسي في أي خدمة OpenID Connect، وبيوضح كل الـ endpoints المتاحة. هتلاقي فيه:

```
"registration_endpoint": "/reg"
```

#### 2. سجّل تطبيق وهمي بتاعك

في **Burp Repeater**، ابعت:

json

```json
POST /reg HTTP/1.1Host: oauth-YOUR-OAUTH-SERVER.oauth-server.netContent-Type: application/json{  "redirect_uris": ["https://example.com"]}
```

ابعت الطلب. لاحظ إنك سجّلت تطبيق **من غير أي مصادقة خالص**، والرد بيديك `client_id` جديد.

#### 3. اكتشف مكان استخدام الـ logo

في صفحة "Authorize" العادية (وقت تسجيل الدخول عن طريق OAuth)، هتلاحظ إن **لوجو التطبيق** بيتعرض، ومصدره:

```
GET /client/CLIENT-ID/logo
```

وبما إن معيار OpenID بيسمح بتحديد `logo_uri` وقت التسجيل، يبقى ده المكان اللي هنستغله.

#### 4. أكد إن logo_uri بيولّد طلب HTTP فعلي (باستخدام Collaborator)

سجّل تطبيق جديد بـ:

json

```json
{  "redirect_uris": ["https://example.com"],  "logo_uri": "https://BURP-COLLABORATOR-SUBDOMAIN"}
```

خد الـ `client_id` الجديد، وابعت:

```
GET /client/NEW-CLIENT-ID/logo
```

روح لتبويب **Collaborator** ودوس **Poll now**. لو شفت تفاعل HTTP، يبقى تأكدنا إن **الخادم فعلاً بيروح يجيب الصورة من الرابط اللي حددناه** — يعني عندنا SSRF قابل للاستغلال.

#### 5. استهدف الـ AWS Metadata Endpoint

سجّل تطبيق جديد بقيمة `logo_uri` تشاور على الهدف الحقيقي:

json

```json
{  "redirect_uris": ["https://example.com"],  "logo_uri": "http://169.254.169.254/latest/meta-data/iam/security-credentials/admin/"}
```

خد الـ `client_id` الجديد من الرد.

#### 6. اجلب النتيجة عن طريق endpoint اللوجو

ابعت:

```
GET /client/NEW-CLIENT-ID/logo
```

بما إن endpoint اللوجو غالبًا بيرجع **محتوى الصورة اللي جابها من الرابط** (أو في حالة الفشل، بيرجع محتوى الـ response كامل كـ "صورة" مش صحيحة)، الرد هيحتوي على **نص الـ response الفعلي** اللي رجع من AWS metadata endpoint — وده هيكون فيه بيانات اعتماد حساسة زي:

json

```json
{  "AccessKeyId": "...",  "SecretAccessKey": "...",  "Token": "..."}
```

#### 7. سلّم الحل

انسخ الـ **Secret Access Key**، وقدّمها في زرار **"Submit solution"** بتاع اللاب.

### ليه ده بيحصل تقنيًا

python

```python
@app.route("/reg", methods=["POST"])def register_client():    data = request.get_json()    client_id = generate_client_id()    save_client(client_id, redirect_uris=data.get("redirect_uris"), logo_uri=data.get("logo_uri"))    # ❌ logo_uri بيتقبل من غير أي تحقق أو whitelist    return jsonify({"client_id": client_id, ...})@app.route("/client/<client_id>/logo")def get_logo(client_id):    client = get_client(client_id)    response = requests.get(client.logo_uri)   # ❌ السيرفر نفسه بيعمل الطلب لأي URL محدد من العميل    return response.content
```

المشاكل الجوهرية مركّبة من عدة نقاط:

1. **Dynamic Client Registration بدون أي مصادقة**: أي حد يقدر يسجل "تطبيق" وهمي بدون التحقق من هويته، وده بيديه سيطرة على بيانات meta-data زي `logo_uri`.
2. **`logo_uri` بيُقبل بدون أي whitelist أو تحقق من إنه URL خارجي شرعي**: مفيش فحص يمنع عناوين داخلية (زي `169.254.169.254` أو `127.0.0.1` أو `192.168.x.x`).
3. **الخادم نفسه بيعمل الطلب HTTP للـ logo_uri (Server-Side Request)**: وهو اللي بيخلي ده SSRF فعلي — السيرفر (اللي عنده صلاحية وصول لموارد داخلية زي AWS metadata) هو اللي بيروح "يزور" الرابط، مش المستخدم.
4. **الـ response بيرجع محتوى الطلب كامل**: حتى لو مش صورة فعلية، السيرفر بيرجع المحتوى الخام، وده بيديك **قدرة قراءة كاملة (Full read SSRF)** على أي مورد داخلي تحدده.

### الدرس المستفاد

- **أي خاصية بتسمح للمستخدم/العميل بتحديد URL بيتم "زيارته" من طرف السيرفر (زي webhook URLs, callback URLs, logo URLs, avatar fetchers) هي سطح هجوم SSRF محتمل** — ولازم تتفحص بنفس الجدية اللي بيتفحص بيها أي URL parameter تقليدي.
- **معايير مفتوحة زي OpenID Connect بتوفر مرونة كبيرة (زي Dynamic Registration)، لكن المرونة دي بتحتاج ضوابط أمان إضافية صارمة** — زي المصادقة على من يقدر يسجل تطبيقات، وWhitelist لعناوين الـ URLs المسموح بيها (منع IP ranges داخلية بالذات زي `169.254.169.254`, `127.0.0.0/8`, `10.0.0.0/8`, إلخ).
- **AWS Metadata Endpoint (169.254.169.254) هدف كلاسيكي وخطير جدًا لأي SSRF على بيئات Cloud** — لأنه بيعطي **بيانات اعتماد فعلية وصالحة** بدون أي مصادقة إضافية طالما الطلب جاي من داخل الشبكة الداخلية للـ instance.
- **Burp Collaborator ضروري لتأكيد الـ SSRF "الأعمى" (blind)** — في الحالة دي مفيش أي رد فعل واضح في الـ response الأول (إحنا مجرد بنسجل تطبيق)، فاحتجنا قناة out-of-band (Collaborator) للتأكد من حدوث الطلب فعليًا قبل ما نستهدف الـ metadata endpoint الحقيقي.
- الحل الصحيح للموقع: **فرض whitelist صارم على أي URL يُقبل من عميل خارجي قبل ما يتعمل بيه أي طلب HTTP من السيرفر**، ومنع أي طلبات لعناوين IP داخلية أو خاصة (private/reserved IP ranges) بشكل قاطع على مستوى الشبكة أو الكود.

## ليه عملنا كل خطوة في الهجوم ده؟ (شرح كامل للمنطق ورا كل حاجة)

خلينا نرجع لسؤال أساسي الأول: **إيه المشكلة اللي بنستغلها فعلاً؟**

المشكلة في جملة واحدة: OAuth server بيسمح لأي حد **يسجل client application** من غير أي تحقق هوية، وبعدين بيثق في بيانات زي `logo_uri` اللي المسجل ده بعتها، ويعمل لها **fetch من السيرفر نفسه**. يعني إحنا هنخلي سيرفر الـ OAuth (اللي عنده صلاحيات ووصول لشبكة داخلية) **يبعت طلبات نيابة عننا**. ده جوهر أي ثغرة SSRF: إنك تخلي سيرفر تاني يبعتلك بيانات من أماكن إنت مش مسموحلك توصلها مباشرة.

دلوقتي نمشي خطوة خطوة ونفهم الهدف من كل واحدة:

### الخطوة 1: تسجيل الدخول العادي (wiener:peter)

**ليه عملنا كده؟**

الخطوة دي مالهاش علاقة مباشرة بالهجوم — هي بس عشان تفهم إزاي الـ OAuth flow بيشتغل في التطبيق ده من الأساس (إزاي بيحصل login بالـ social media). الهدف الحقيقي مش التطبيق (Client Application) نفسه، الهدف هو **OAuth Provider** اللي بيقف وراه. يعني إحنا بس بنعمل استكشاف (recon) عادي.

### الخطوة 2: قراءة `/.well-known/openid-configuration`

**ليه عملنا كده؟**

عشان نلاقي **خريطة كاملة** لكل الـ endpoints بتاعة الـ OAuth server من غير ما نخمن أو نجرب عشوائي. الملف ده بيرجع JSON فيه كل حاجة: فين الـ authorization endpoint، فين الـ token endpoint... إلخ.

**النقطة الحرجة اللي دورنا عليها تحديداً:**

json

```json
"registration_endpoint": "https://.../reg"
```

لو الحقل ده موجود، ده معناه إن السيرفر بيدعم **Dynamic Client Registration** (حسب RFC 7591). الميزة دي أصلاً معمولة عشان تسهّل على تطبيقات تسجل نفسها تلقائياً كـ OAuth clients من غير تدخل بشري (Admin مايحتاجش يعمل تسجيل يدوي لكل تطبيق جديد).

المشكلة: الميزة دي **قوية جداً وخطيرة لو اتسابت من غير حماية**، لأنها معناها "أي حد يقدر يسجل نفسه كـ client رسمي عند الـ OAuth provider".

### الخطوة 3: اختبار `/reg` بطلب بسيط

**ليه عملنا كده؟**

عشان نتأكد **هل الـ endpoint ده فعلاً شغال ومفتوح من غير أي auth؟** بعتنا أقل بيانات ممكنة (`redirect_uris` بس، لأنه الحقل الإجباري الوحيد حسب الـ spec) عشان نشوف رد فعل السيرفر.

**النتيجة المهمة:**

```
HTTP/1.1 201 Created
{ "client_id": "...", "client_secret": "..." }
```

السيرفر **وافق ورجعلنا client_id و client_secret فعلياً** — من غير ما يطلب منا نسجل دخول، من غير API key، من غير أي حاجة. ده تأكيد إن **أي حد على الإنترنت يقدر يسجل نفسه كـ OAuth client رسمي على السيرفر ده**. الخطوة دي هي أول "إثبات وجود ثغرة" (confirmation)، من غير استغلال فعلي لسه.

### الخطوة 4: اكتشاف آلية عرض اللوجو (`/client/{id}/logo`)

**ليه عملنا كده؟**

لسه معندناش هدف SSRF فعلي — عندنا بس "تسجيل مفتوح". محتاجين نلاقي **حاجة في السيرفر بتستخدم بيانات إحنا بعتناها** وبتعمل بيها حاجة server-side.

لاحظنا إن أثناء الـ consent screen، السيرفر بيعرض **لوجو بتاع الـ client**. اللوجو ده جاي منين؟ من `logo_uri` اللي إحنا حطيناه وقت التسجيل! يبقى المنطق كده:

```
إحنا بنتحكم في logo_uri (وقت التسجيل)
        ↓
السيرفر بيعمل fetch لـ logo_uri دي وقت ما حد يطلب /client/{id}/logo
        ↓
لو مفيش تحقق من الـ URL → SSRF محتملة
```

هنا لقينا الـ **"gadget"** بتاعنا — الميكانيزم اللي هنستغله.

### الخطوة 5: التأكيد باستخدام Burp Collaborator

**ليه عملنا كده؟**

عشان نتأكد **100%** إن السيرفر فعلاً بيعمل HTTP request حقيقي للـ `logo_uri`، مش مجرد إنه بيخزنها كنص أو بيعرضها كـ `<img src="">` في متصفح الضحية (لو كانت الحالة التانية، مكانش هيبقى SSRF، كان هيبقى مجرد XSS/HTML injection عادي في متصفح المستخدم).

Burp Collaborator بيديك domain فريد بتتحكم فيه، ولما تحط لينك بيه في `logo_uri` وتستنى تفاعل، لو السيرفر عمل طلب فعلي لـ domain ده — يبقى إحنا أكدنا إن **السيرفر نفسه (مش متصفح حد تاني) هو اللي بيعمل الـ request**. ده الفرق الجوهري بين SSRF (سيرفر بيطلب) و XSS (متصفح بيطلب).

النتيجة: شفنا request جاي من الـ Collaborator، ومصدره IP بتاع السيرفر — يبقى SSRF مؤكدة server-side.

### الخطوة 6-9: استهداف AWS Metadata Service (169.254.169.254)

**ليه اخترنا الـ IP ده تحديداً؟**

`169.254.169.254` هو **link-local address خاص** موجود بس جوه أي جهاز شغال على AWS EC2. مفيش حد بره الـ instance نفسه يقدر يوصله مباشرة من الإنترنت — لكن **أي حاجة شغالة جوه الـ instance نفسه** (زي السيرفر بتاعنا) تقدر توصله عادي.

الـ endpoint ده بيدي معلومات عن الـ instance، وأخطر حاجة فيه: **مسار الـ IAM credentials**:

```
/latest/meta-data/iam/security-credentials/[role-name]/
```

لو السيرفر شغال بدور IAM معين (Role) وعنده صلاحيات على AWS، أي حد يقدر يخليه يعمل request للمسار ده هياخد **مفاتيح AWS مؤقتة صالحة فعلياً** لنفس الصلاحيات بتاعة السيرفر ده.

**ليه دي أخطر نقطة في الهجوم كله؟**

لأن SSRF عادي بيديك "قراءة" لموارد داخلية بس، لكن هنا إحنا استخدمناها عشان نسرق **credentials فعلية** ممكن نستخدمها بعد كده على AWS CLI أو API مباشرة — يعني الهجوم اتحول من "تسريب معلومة" لـ **"استيلاء كامل محتمل على حساب AWS"**.

**الخطوات العملية (6، 8، 9) بترجع لنفس المنطق:**

1. سجّل client جديد وحط الـ `logo_uri` = رابط الـ AWS metadata endpoint
2. اطلب `/client/{new_id}/logo` — ده اللي بيخلي السيرفر ينفذ الطلب الداخلي فعلياً
3. الرد اللي بيرجعلك في الـ response هو **نفس محتوى الـ metadata endpoint** — يعني إحنا استخدمنا السيرفر كـ "بروكسي" بينا وبين شبكته الداخلية

### ليه الثغرة دي بالذات (SSRF via dynamic registration) حصلت أصلاً؟

لو نرجع نلخص الأسباب الجذرية (زي ما موضح في المستند):

| السبب | التفسير |
| --- | --- |
| **Registration مفتوح** | الـ spec (RFC 7591) بتقول "SHOULD require authentication" — يعني توصية مش إجبار، والمطور هنا تجاهلها |
| **مفيش تحقق من `logo_uri`** | السيرفر بيثق عمياني في أي URL المستخدم بعتها ويعمل لها fetch من غير whitelist أو فلترة |
| **مفيش عزل شبكي (network segmentation)** | حتى لو حصل SSRF، المفروض السيرفر يكون معزول عن الموارد الحساسة زي الـ metadata endpoint، لكن هنا مفيش أي حماية إضافية |

الثلاث نقط دول مجتمعين هما اللي خلوا هجوم بسيط (تسجيل client) يتحول لـ **اختراق كامل لحساب AWS**.
