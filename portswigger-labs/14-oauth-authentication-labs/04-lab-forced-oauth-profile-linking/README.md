اللاب ده بيجمع بين **OAuth vulnerability** و**CSRF (Cross-Site Request Forgery)** — وده مثال ممتاز على إزاي ثغرتين من فئتين مختلفتين ممكن يتضافروا مع بعض عشان ينتجوا هجوم خطير جدًا.

### طبيعة الثغرة (السياق)

الموقع بيدّيك خيار **"ربط" (link/attach)** حساب السوشيال ميديا بتاعك بحسابك الحالي على الموقع، عشان تقدر تسجل دخول عن طريق OAuth بدل الباسورد العادي في المرات الجاية.

المشكلة: **عملية الربط دي (Attach a social profile) بتفتقر لحماية CSRF** — تحديدًا، طلب الـ authorization في الـ OAuth flow **معندوش `state` parameter**. الـ `state` parameter في OAuth مصمم أصلاً عشان **يربط طلب الـ authorization بجلسة المستخدم اللي بدأ العملية**، ويمنع أي حد يقدر "يكمّل" عملية OAuth نيابة عن حد تاني.

### الفكرة الذكية في الاستغلال

بما إن عملية "ربط حساب سوشيال ميديا" **مش محمية بـ CSRF**، المهاجم يقدر:

1. **يبدأ عملية الربط بحسابه هو** (حساب السوشيال ميديا بتاعه).
2. **يسرق الـ authorization code** اللي بيرجع في نص العملية (**قبل ما يستخدمه هو نفسه**).
3. **يخلي الضحية (بجلسته النشطة على الموقع) يستخدم الـ code ده بدلاً منه** — عن طريق حقن الرابط في صفحة (زي `<iframe>`) وتوصيلها للضحية.
4. النتيجة: **حساب السوشيال ميديا بتاع المهاجم بيترتبط بحساب الضحية** (مش حساب المهاجم)! لأن الـ code بيتم "استهلاكه" في سياق **جلسة الضحية**، والموقع بيفترض إن "اللي بيكمل عملية الربط دلوقتي هو نفس الشخص اللي بدأها" — لكن بسبب غياب الـ `state`، محدش أكد إن ده صحيح.

بعد كده، المهاجم يقدر **يسجل دخول بحساب السوشيال ميديا بتاعه هو**، وبما إنه **مربوط دلوقتي بحساب الضحية**، هيدخل مباشرة على **حساب الضحية نفسه**.

### خطوات الحل بالتفصيل

#### 1. سجل دخول عادي واستكشف خاصية الربط

دوس **"My account"**، سجل دخول بحسابك العادي (`wiener:peter`). هتلاحظ خيار **"Attach a social profile"**.

#### 2. اربط حسابك بحساب السوشيال ميديا بتاعك (للتجربة والفهم)

دوس **"Attach a social profile"**، هتتحول لموقع السوشيال ميديا، سجل دخول بـ `peter.wiener:hotdog`، وكمّل عملية الـ OAuth. هترجع للمدونة وحسابك اتربط.

#### 3. جرب تسجيل الدخول بالسوشيال ميديا

اعمل logout، وسجل دخول تاني باختيار **"Log in with social media"** — هتلاقي نفسك بتدخل فورًا بحسابك، وده بيأكد إن الربط اشتغل صح.

#### 4. افحص الـ OAuth flow في Burp

راجع **Proxy history**، ولاحظ في طلب:

```
GET /auth?client_id=[...]
```

إن الـ `redirect_uri` بيوجّه لـ `/oauth-linking`. **المهم**: لاحظ إن الطلب **معندوش `state` parameter** — ده هو الثغرة اللي هنستغلها.

#### 5. اسرق authorization code جديد (بدون ما تستخدمه)

1. فعّل **Proxy interception** (Intercept is on).
2. دوس **"Attach a social profile"** تاني (بنفس حسابك، `peter.wiener`).
3. في Burp Proxy، مرّر الطلبات (Forward) لحد ما توصل لـ:

```
   GET /oauth-linking?code=[...]
```

1. كليك يمين على الطلب ده واختار **"Copy URL"** — عشان تاخد الـ URL كامل بالـ code.
2. **اعمل Drop للطلب** (متمررهوش) — ده **مهم جدًا** عشان تضمن إن الـ code **ماتم استهلاكه** بحسابك انت، وبالتالي **يفضل صالح (valid)** للاستخدام لاحقًا.

#### 6. أوقف الـ interception واعمل logout

أوقف Proxy interception، واعمل logout من الموقع.

#### 7. جهّز الـ Exploit (iframe)

روح لـ **exploit server**، واعمل صفحة فيها:

#### 8. سلّم الـ Exploit للضحية (Admin)

دوس **"Deliver exploit to victim"**. الـ admin (اللي دايمًا عنده session نشطة على الموقع) هيفتح الصفحة، والـ `iframe` هيحمّل الرابط ده **في سياق جلسته هو**، وده هيخلي الموقع **يربط حساب السوشيال ميديا بتاع المهاجم (`peter.wiener`) بحساب الـ admin نفسه** — من غير ما الـ admin ياخد أي بلاغ أو يوافق صراحة.

#### 9. سجل دخول بحساب السوشيال ميديا بتاعك

ارجع للموقع، اختار **"Log in with social media"**، وسجل دخول بنفس بيانات السوشيال ميديا بتاعتك (`peter.wiener:hotdog`).

بما إن الحساب ده **دلوقتي مربوط بحساب الـ admin** (بسبب هجوم الـ CSRF)، هتدخل **مباشرة كـ admin**!

#### 10. احذف carlos

روح لصفحة الأدمن بانل، واحذف `carlos`. اللاب هيتحل تلقائيًا ✅.

### ليه ده بيحصل تقنيًا

python

```python
@app.route("/oauth-linking")def oauth_linking():    code = request.args.get("code")    # ❌ مفيش أي state parameter يتحقق منه!    access_token = exchange_code_for_token(code)    social_profile = get_social_profile(access_token)    current_user = get_logged_in_user(session)   # ❌ بياخد "المستخدم الحالي" من جلسة الضحية    link_social_profile(current_user, social_profile)    return redirect("/my-account")
```

المشكلة الجوهرية: **الـ `code` بيتم "استهلاكه" في سياق أي جلسة (session) بتفتح الرابط ده**، وبما إن **مفيش `state` parameter بيربط بين "مين بدأ العملية" و"مين هيكمّلها"**، أي حد (المهاجم) يقدر:

1. يبدأ العملية (يجيب `code` صالح).
2. **يخلي حد تاني (الضحية) يكمّل العملية دي** من خلال جلسته هو.
3. النتيجة: **الربط بيحصل بين "حساب السوشيال ميديا بتاع المهاجم" و"حساب الضحية على الموقع"**، مش العكس.

### الفرق بين ده وبين CSRF التقليدي

في CSRF التقليدي، المهاجم بيخلي الضحية "تعمل فعل" (زي تحويل فلوس) بدون علمها. هنا الفكرة مشابهة لكن **أعمق**: المهاجم بيخلي الضحية **"تكمل نص عملية OAuth بدأها المهاجم نفسه"** — وده بيقلب المعادلة: **بدل ما يكون المهاجم هو اللي بياخد وصول لحساب الضحية مباشرة، هو بيخلي الضحية "تربط نفسها" بحساب المهاجم من غير قصد**.

### الدرس المستفاد

- **الـ `state` parameter في OAuth مش اختياري أو تجميلي** — هو **آلية حماية أساسية ضد CSRF**، ولازم يكون:
    - **عشوائي وغير قابل للتخمين**.
    - **مرتبط بجلسة المستخدم اللي بدأ الطلب**.
    - **يتفحص بدقة عند اكتمال العملية**، للتأكد إن نفس المستخدم اللي بدأ هو نفسه اللي بيكمّل.
- **أي عملية بتغيّر حالة حساس (زي ربط حساب، تغيير إيميل، تغيير باسورد) لازم تكون محمية بـ CSRF token**، مش بس عمليات "الفعل المباشر" التقليدية زي تحويل الفلوس.
- **الـ iframe تقنية قوية لتنفيذ هجمات CSRF بصمت**، لأنها بتخلي المتصفح يحمّل الرابط ويبعت الكوكيز المرتبطة بيه (session بتاعة الضحية) تلقائيًا، من غير أي تفاعل ظاهر أو تحويل واضح للصفحة.
- **خصائص "الراحة" زي "ربط حساب سوشيال ميديا للدخول السريع" بتحتاج نفس مستوى الحماية الأمنية** زي أي عملية حساسة تانية — لأنها فعليًا بتغيّر **طريقة الوصول لحسابك بالكامل**.
- ده مثال ممتاز على إزاي **دمج ثغرتين من فئتين مختلفتين (OAuth flaw + CSRF) بينتج عنه Account Takeover كامل**، حتى لو كل ثغرة لوحدها كانت هتبان "أقل خطورة".
