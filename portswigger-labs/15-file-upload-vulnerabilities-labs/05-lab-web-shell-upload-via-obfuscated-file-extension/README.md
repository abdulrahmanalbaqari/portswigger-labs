# Lab : Web shell upload via obfuscated file extension

https://portswigger.net/web-security/file-upload/lab-file-upload-web-shell-upload-via-obfuscated-file-extension

- الفكره من الLab ده ان function تحميل الصور بتعمل حظر علي ملفات الphp فا احنا استخدمنا obfuscated file extension دي بتخلي الكومبيوتر يفهم الكلام بس البشر لا فا احنا عملنا بيها extension فوق الphpوحطينا %00 ساعتها احنا مكسرناش الrole بس اول متخش علي الserver هتتعامل ولا كانها موجوده

```bash
1. filename="test1.php%00.JPG"

2. <?php echo file_get_contents('/home/carlos/secret'); ?>

3. GET /files/avatars/test1.php
```

اللاب ده كمان من فئة **File Upload Vulnerabilities**، لكن الاستغلال هنا مختلف تمامًا عن اللاب السابق. هنا الحماية أقوى شوية — **whitelist حقيقية** (بتسمح بـ JPG وPNG بس)، لكن فيها **ثغرة كلاسيكية جدًا**: **Null Byte Injection** في اسم الملف.

### المفهوم الأساسي: Null Byte Injection

زي ما شرحنا قبل كده في لاب الـ Path Traversal (**"validation of file extension with null byte bypass"**)، المشكلة هنا نفس الفكرة **بالظبط**، بس مطبقة في سياق **File Upload** بدل قراءة ملفات.

الفكرة: بعض اللغات (خصوصًا PHP في إصداراته الأقدم، أو أي كود بيتفاعل مع مكتبات مبنية على C) بتتعامل مع **البايت الفارغ (Null Byte - `\0` أو مُرمّز كـ `%00`)** على إنه **نهاية النص (string terminator)** — تمامًا زي طبيعة الـ strings في لغة C.

### طبيعة الثغرة في اللاب ده

الموقع بيتحقق من **اسم الملف بالكامل** عشان يتأكد إنه بينتهي بـ `.jpg` أو `.png` (Whitelist حقيقية هنا، على عكس اللاب السابق). لكن الفحص ده بيتم **على مستوى اللغة اللي بتشوف الـ string كامل**، بينما **حفظ الملف الفعلي على القرص** بيحصل من خلال **دالة نظام تشغيل بتقطع الاسم عند أول null byte تقابله**.

### خطوات الحل بالتفصيل

#### 1. سجل دخول وارفع صورة عادية

سجل دخول بـ `wiener:peter`، وارفع صورة عادية كـ avatar، وسجّل الـ URL بتاعها.

#### 2. جهّز طلب الجلب في Repeater

في **Proxy > HTTP history**، لاقي:

```
GET /files/avatars/<YOUR-IMAGE>
```

ابعته على **Burp Repeater** — هنستخدمه لاحقًا للتأكد من الاستغلال.

#### 3. جهّز الـ PHP Web Shell

اعمل ملف `exploit.php`:

php

```php
<?php echo file_get_contents('/home/carlos/secret'); ?>
```

#### 4. جرب ترفعه مباشرة

هيترفض برسالة توضح إن **بس JPG وPNG** مسموح بيهم — يبقى تأكدنا إن فيه **whitelist حقيقية** هنا (مش زي اللاب السابق اللي كانت blacklist).

#### 5. ابعت طلب الرفع على Repeater

لاقي طلب `POST /my-account/avatar` في الـ history، وابعته على **Burp Repeater**.

#### 6. حقن الـ Null Byte في اسم الملف

في جسم الطلب، في هيدر **`Content-Disposition`**، لاقي قيمة الـ `filename`، وغيّرها من:

```
filename="exploit.php"
```

لـ:

```
filename="exploit.php%00.jpg"
```

**الشرح**:

- `%00` هو **الترميز URL-encoded** للـ null byte.
- إحنا كده بعتنا اسم ملف **ظاهريًا بينتهي بـ `.jpg`** — فالفحص اللي بيدور على `.jpg` في نهاية الاسم **هيعدي بنجاح**.
- لكن لما السيرفر يحاول **يحفظ الملف فعليًا على القرص**، الدالة اللي بتتعامل مع اسم الملف (لو مبنية على مكتبة C قديمة) **هتوقف عند أول `\0`**، وهتحفظ الملف باسم:

```
  exploit.php
```

(من غير `.jpg` خالص، لأن كل حاجة بعد الـ null byte اتجاهلت تمامًا).

#### 7. ابعت الطلب وتأكد من النجاح

هتلاحظ إن الرفع **نجح**، ورسالة التأكيد بتشير للملف باسم **`exploit.php`** (مش `exploit.php%00.jpg`) — ده تأكيد إن الـ null byte والامتداد اللي بعده **اتقطعوا فعلاً** أثناء الحفظ.

#### 8. نفّذ الملف واستخرج السر

ارجع لتاب Repeater التاني (`GET /files/avatars/...`)، واستبدل اسم الصورة بـ:

```
exploit.php
```

ابعت الطلب. بما إن الملف **اتخزن فعليًا بامتداد `.php` حقيقي** (بفضل الـ null byte trick)، هيتنفذ كـ PHP عادي، وهيرجعلك **محتوى `/home/carlos/secret`** في الـ response.

#### 9. سلّم الحل

قدّم السر اللي ظهر في زرار **"Submit solution"**.

### ليه ده بيحصل تقنيًا

python

```python
def upload_avatar(file):    filename = file.filename   # "exploit.php\x00.jpg"    # ✅ الفحص بيشتغل على النص الكامل، وبيلاقي .jpg في الآخر    if not (filename.endswith(".jpg") or filename.endswith(".png")):        return "Only JPG and PNG allowed", 403    # ❌ لكن دالة الحفظ (لو مبنية على مكتبة C قديمة) بتقطع عند null byte    save_path = f"/files/avatars/{filename}"    with open(save_path, "wb") as f:   # النظام بيوقف عند \x00، فبيتحفظ الملف باسم "exploit.php" بس        f.write(file.content)
```

المشكلة الجوهرية: **تناقض بين طبقتين تتعاملان مع نفس الـ string بشكل مختلف**:

- **طبقة الفحص (Validation layer)**: بتشوف الـ **string كامل** (زي أي لغة حديثة بتتعامل مع الـ strings كـ arrays من الحروف بطول محدد، مش بـ null-terminated).
- **طبقة حفظ الملف (Filesystem layer)**: لو معتمدة على مكتبات أو استدعاءات نظام تشغيل قديمة (زي بعض دوال C)، بتتعامل مع الـ string على إنه **بينتهي عند أول `\0`**.

هنا بالظبط نفس النمط اللي شرحناه في لاب الـ path traversal null byte، لكن مطبّق في سياق **رفع الملفات** بدل **قراءتها**.

### الفرق الجوهري عن اللاب السابق

|  | **اللاب السابق (Blacklist bypass)** | **اللاب ده (Null Byte)** |
| --- | --- | --- |
| **نوع الحماية** | Blacklist (بتمنع امتدادات معينة) | **Whitelist حقيقية** (بتسمح بس بـ JPG/PNG) |
| **الثغرة المستغلة** | إمكانية "تعليم" امتداد جديد قابل للتنفيذ عن طريق `.htaccess` | خداع الفحص بجعله يرى امتداد مختلف عن اللي هيتخزن فعليًا |
| **عدد الملفات المطلوبة** | 2 (ملف `.htaccess` + ملف الشيل بامتداد جديد) | 1 بس (ملف واحد بامتداد مزيّف عن طريق null byte) |

### الدرس المستفاد

- **حتى الـ Whitelist "الحقيقية" مش كافية لوحدها**، لو الفحص بيحصل على تمثيل مختلف للـ string عن اللي بيُستخدم فعليًا وقت الحفظ على القرص — لازم **كل الطبقات تتعامل مع نفس البيانات بنفس الطريقة بالظبط**.
- **Null Byte Injection ثغرة قديمة نسبيًا** (زي ما ذكرنا في لاب path traversal المشابه)، لكنها **لسه موجودة في أنظمة legacy** أو أي كود بيعتمد على مكتبات قديمة مش بتتعامل بأمان مع الـ null bytes في الأسماء.
- **الحل الصحيح**: بعد الفحص، لازم يتم **تنظيف اسم الملف بالكامل (sanitization)** — يعني رفض أو إزالة أي null bytes صراحة، أو الأفضل: **توليد اسم ملف جديد بالكامل من السيرفر** (زي UUID عشوائي + الامتداد المتحقق منه فعليًا)، بدل الاعتماد على اسم الملف الأصلي المُقدّم من المستخدم بأي شكل.
- **فحص محتوى الملف الفعلي (Magic Bytes)** بالإضافة لفحص الامتداد **يقلل من فعالية هجمات زي دي**، لأن حتى لو الاسم اتخدع، محتوى الملف (اللي هو كود PHP نصي) **مش هيطابق التوقيع البنيوي (binary signature) الحقيقي لملف JPG أو PNG**.
- هجمات **Null Byte** بتوضح مبدأ عام مهم: **أي اختلاف في طريقة تفسير نفس البيانات بين طبقتين مختلفتين من نفس النظام (حتى لو الاتنين "صح" من منظورهم الخاص) هو ثغرة كامنة** — نفس المبدأ اللي شفناه يتكرر في السياقات المختلفة اللي شرحناها (path traversal، cache poisoning، email parsing، OAuth redirect_uri).
