# What is Essential skills ?

# Essential Skills — المهارات الأساسية للانتقال من اللابات للاختبار الحقيقي

## ليه القسم ده مهم؟

كل اللابات اللي شرحناها من الأول (path traversal، access control، authentication، OAuth، file upload، إلخ) بتوضح **نموذج واحد محدد** لكل ثغرة. لكن في الواقع، مواقع حقيقية:

- **اتعملها audit قبل كده** من مختبرين تانيين.
- **اتعمل لها patches** جزئية بتمنع الـ payloads "الكلاسيكية" اللي في اللابات.
- بتستخدم **فلاتر ومكتبات حماية (WAFs)** بتدور على أنماط معروفة.

يعني لو نسخت نفس الـ payload بالظبط من لاب وحاولت تستخدمه على موقع حقيقي، غالبًا **هيترفض**. المهارة الحقيقية هي **إنك تفهم الفكرة الجوهرية للثغرة**، مش بس تحفظ payload معين، عشان تقدر **تعدّل وتتكيف** مع أي عائق جديد تقابله.

## 1. Obfuscating Attacks Using Encodings (التمويه باستخدام الترميز)

### الفكرة

فلاتر الإدخال (input filters) غالبًا بتدور على **نمط نصي معين حرفي** (زي `<script>` أو `' OR 1=1`). لو غيّرت شكل الـ payload بترميز مختلف **بينفس المعنى النهائي بعد فك الترميز**، ممكن تتخطى الفلتر **لو الفلتر بيفحص قبل فك الترميز، لكن السيرفر بيفسّر بعده**.

### أمثلة عملية من اللي شرحناه قبل كده

| السياق | التقنية | مثال |
| --- | --- | --- |
| Path Traversal | URL encoding | `..%2f..%2f..%2fetc/passwd` بدل `../../../etc/passwd` |
| Path Traversal | Double URL encoding | `%252e%252e%252f` |
| Path Traversal | Non-recursive stripping | `....//` بدل `../` |
| Email validation | Encoded-word / UTF-7 | `=?utf-7?q?&AGEAYgBj-?=` |
| Null byte | URL-encoded null | `exploit.php%00.jpg` |

### أنواع ترميز تانية مفيدة تستحق التجربة

- **HTML entity encoding**: `&#x3C;script&#x3E;` بدل `<script>`.
- **Unicode escaping**: `\u003Cscript\u003E`.
- **Case variation**: `ScRiPt` بدل `script` (لو الفلتر case-sensitive).
- **Mixed encoding**: خلط أكتر من نوع ترميز في نفس الـ payload.

### الدرس الأهم

> أي مكان فيه **اختلاف في توقيت أو طريقة فك الترميز بين طبقة الفلترة وطبقة التنفيذ الفعلي**، هو نقطة ضعف محتملة. اللاب المرتبط (**SQL injection with filter bypass via XML encoding**) بيوضح نفس المبدأ في سياق XML entities.
> 

## 2. استخدام Burp Scanner أثناء الاختبار اليدوي

### الفكرة

بعض الثغرات (زي SQLi، XSS) بتحتاج **تجربة عشرات أو مئات الـ payloads** في كل حقل إدخال — ده مستحيل تعمله يدويًا بكفاءة في وقت محدود. **Burp Scanner** أداة أتمتة بتقدر:

- تفحص كل الحقول تلقائيًا بمكتبة ضخمة من الـ payloads.
- تكتشف أنماط استجابة مشبوهة (زي أخطاء SQL، تأخير زمني في blind injection).

### الاستراتيجية الصح للجمع بين الاثنين

- استخدم **Burp Scanner للمسح الأولي السريع** على كل نقاط الإدخال — ده بيوفر وقتك ويقلل احتمالية إنك تفوت حاجة.
- ركّز **مجهودك اليدوي وخبرتك** على:
    - **استغلال (exploit)** أي نتيجة اكتشفها الـ Scanner (لأن الأداة بتكتشف وجود الثغرة، لكن مش دايمًا بتبني استغلال كامل).
    - **تسلسل الثغرات (chaining)** — زي كل الأمثلة اللي شرحناها (path traversal + host header، OAuth + open redirect، إلخ) — ده شيء الأدوات الأوتوماتيكية **ضعيفة فيه جدًا**، لأنه بيحتاج فهم وربط منطقي بين نتائج مختلفة.
    - الثغرات المنطقية (**Business Logic Flaws**) زي كل اللابات اللي شرحناها (2FA broken logic، password reset poisoning، إلخ) — دي **شبه مستحيل** إن أداة تكتشفها تلقائيًا، لأنها بتحتاج **فهم لمنطق العمل الخاص بالموقع نفسه**.

### نصيحة عملية

Burp Scanner ممتاز لثغرات **"الأنماط المعروفة"** (SQLi, XSS, XXE)، لكنه **لا يغني أبدًا** عن الفحص اليدوي لثغرات منطقية أو معقدة زي اللي اتعلمناها في السلاسل اللي فاتت (Access Control, Authentication logic, OAuth chaining).

## 3. اكتشاف ثغرات غير معروفة مسبقًا (Mystery Lab)

### الفكرة

في كل اللابات اللي حللناها سوا، كان عندك **معلومة أساسية جدًا**: اسم الثغرة ووصفها. في الواقع، **محدش هيقولك "الموقع ده فيه IDOR" أو "فيه SSRF"** — لازم انت تكتشف ده بنفسك من الصفر.

**Mystery Lab Challenge** ميزة من PortSwigger بتحاكي السيناريو الحقيقي ده: بتدّيك موقع فيه ثغرة **من غير ما تقولك نوعها**، وعليك إنك:

1. تستكشف الموقع بمنهجية (systematic exploration).
2. تلاحظ أي سلوك غريب أو غير متوقع.
3. تربط الملاحظة دي بفئة ثغرة من اللي اتعلمتها.
4. تستغلها.

### منهجية عملية لمواجهة "مجهول" (زي ما اتعلمنا من كل اللابات اللي فاتت)

بناءً على كل الأنماط اللي شرحناها في المحادثة دي، فيه **checklist ذهنية** تقدر تطبقها على أي موقع مجهول:

1. **افحص كل نقطة بتاخد input من المستخدم** — مش بس الفورمات الظاهرة (Login, Search)، لكن كمان الـ headers (Host, X-Forwarded-*, Referer)، الكوكيز، والـ query parameters المخفية.
2. **دوّر على IDs يمكن تغييرها** (أرقام، usernames في الـ URL) — أول اشتباه في IDOR.
3. **افحص أي عملية متعددة الخطوات** (registration, password reset, OAuth) — دايمًا اسأل: "هل كل خطوة بتتحقق من صلاحياتها لوحدها، ولا بتفترض إن اللي قبلها كانت كافية؟"
4. **افحص رسائل الخطأ بعناية** — أي فرق بسيط بين رسالتين ممكن يكون Information Disclosure أو Enumeration.
5. **جرب الحالات الحدّية (edge cases)**: نصوص طويلة جدًا، null bytes، أحرف Unicode غريبة، أكتر من هيدر بنفس الاسم.
6. **افحص أدوات الـ Content Discovery** (زي في لاب inconsistent handling) — مسارات مخفية زي `/admin`, `/.git/`, `/backup`.
7. **لو لقيت ثغرة "صغيرة"، افكر: تقدر تربطها بحاجة تانية؟** (زي path traversal + host header = SSRF متقدم، أو open redirect + OAuth = token theft).

## الخلاصة: الفرق بين "حل لاب" و"اختبار اختراق حقيقي"

| **حل لاب** | **اختبار حقيقي (Real-world pentesting)** |
| --- | --- |
| تعرف نوع الثغرة مقدمًا | لازم تكتشفها بنفسك من الصفر |
| الـ payload المعروف بيشتغل غالبًا | محتاج تموّه وتكيّف الـ payload باستمرار |
| ثغرة واحدة معزولة | غالبًا محتاج تربط عدة ثغرات صغيرة مع بعض |
| بيئة نظيفة بدون حماية إضافية | فيه WAFs، فلاتر، patches جزئية |
| هدف واضح ("احذف carlos") | الهدف بيتحدد بعد ما تكتشف الثغرة أصلاً |

القيمة الحقيقية اللي المفروض تاخدها من كل اللابات اللي شرحناها مش حفظ الخطوات، لكن **فهم النمط الجوهري وراء كل ثغرة** — عشان لما تقابل نسخة مختلفة شكليًا منها في موقع حقيقي، تعرف تتعرف عليها وتتكيف معاها.
