# what is Race conditions ?

## شرح الـ Race Conditions (ثغرات التزامن)

### أولاً: إيه الفكرة؟

الـ **Race Condition** بتحصل لما السيرفر يعالج أكتر من request في نفس الوقت (Concurrently) من غير حماية كافية. النتيجة إن أكتر من Thread يتعاملوا مع **نفس البيانات** في نفس اللحظة، فيحصل "تصادم" (Collision) وسلوك غير متوقع.

#### مثال بسيط: كوبون خصم بيتستخدم مرة واحدة

السيرفر بيعمل 3 خطوات:

1. يتأكد إنك ماستخدمتش الكوبون قبل كده (**Check**)
2. يطبق الخصم
3. يسجل في الداتابيز إنك استخدمته (**Update**)

لو بعت request واحد، كله تمام. لكن لو بعت **اتنين في نفس الجزء من الثانية**، الـ request التاني هيعدّي الخطوة 1 قبل ما الأول يوصل للخطوة 3، فالاتنين يشوفوا إن الكوبون "لسه ما اتستخدمش"، والخصم يتطبق مرتين.

الفترة الزمنية الصغيرة دي (أجزاء من الثانية) اسمها **Race Window**، والحالة المؤقتة اللي السيرفر بيمر بيها اسمها **Sub-state**.

> **التشبيه:** اتنين بيسحبوا من نفس الحساب في ATM عن طريق كارتين مختلفين في نفس اللحظة. كل ماكينة بتقرأ الرصيد 1000 وتصرف 1000، قبل ما أي واحدة تحدّث الرصيد.
> 

النوع ده اسمه **TOCTOU** (Time-of-Check to Time-of-Use): الفحص في لحظة، والاستخدام في لحظة تانية، والحالة اتغيرت بينهم.

### ثانياً: أنواع الثغرة في الشرح

#### 1. Limit Overrun (تجاوز الحد)

أشهر نوع. أمثلة:

- استخدام Gift Card أكتر من مرة
- تقييم منتج أكتر من مرة
- سحب أو تحويل فلوس أكتر من الرصيد
- إعادة استخدام حل CAPTCHA واحد
- تخطي الـ Rate Limit بتاع الـ Brute Force (تبعت 100 محاولة باسورد قبل ما العداد يتحدّث)

#### 2. Hidden Multi-step Sequences (خطوات مخفية)

request واحد بيعمل جواه سلسلة خطوات. مثال MFA:

```
session['userid'] = user.userid        ← هنا المستخدم بقى Logged in
if user.mfa_enabled:
    session['enforce_mfa'] = True      ← هنا بس بيتفعّل فرض الـ MFA
```

بين السطرين في Sub-state: المستخدم عنده Session صالحة **بس الـ MFA لسه مش مفروض**. المهاجم يبعت Login + request لصفحة حساسة في نفس اللحظة، فيدخلها من غير كود الـ MFA.

#### 3. Multi-endpoint Race Conditions

التصادم بين **endpoints مختلفة**. مثال المتجر: الدفع اتأكد، لكن الطلب لسه ما اتأكدش. لو ضفت منتجات للسلة في الـ window دي، هتدفع على منتج واحد وتستلم أكتر.

#### 4. Single-endpoint Race Conditions

نفس الـ endpoint بقيم مختلفة. مثال Password Reset:

- المهاجم يطلب reset لنفسه ولـ victim في نفس اللحظة من نفس الـ Session
- الـ Session تنتهي بـ `reset-user = victim` لكن `reset-token` بتاع المهاجم (اللي اتبعت على إيميله)
- فيستخدم التوكن يغيّر باسورد الضحية

#### 5. Partial Construction

التطبيق بيعمل الـ object على خطوات. مثلاً ينشئ المستخدم الأول، وبعدها بـ statement تانية يحط الـ API Key. في الفاصل ده الـ API key فاضي. المهاجم يبعت `api-key[]=` فيتحول لـ array فاضي أو null، وممكن يطابق القيمة الفاضية ويعدّي التحقق.

#### 6. Time-sensitive Attacks

لو التوكن متولد من **Timestamp** بدل عشوائية قوية، تقدر تطلب reset لمستخدمين في نفس الميلي ثانية فيطلع **نفس التوكن** للاتنين.

### ثالثاً: التقنيات اللي بتخلي الهجوم ينجح

المشكلة الأساسية هي الـ **Network Jitter**: التأخير العشوائي في الشبكة بيخلي الـ requests توصل بترتيب مختلف.

| التقنية | الاستخدام |
| --- | --- |
| **Last-byte sync** | لـ HTTP/1: تبعت كل الـ request إلا آخر byte، وبعدين تبعت الـ bytes الأخيرة مع بعض |
| **Single-packet attack** | لـ HTTP/2: تحط 20-30 request في **TCP packet واحد**، فبتختفي مشكلة الـ jitter تماماً |
| **Connection warming** | تبعت requests عادية الأول (زي GET للـ homepage) عشان تسخّن الاتصال بين الـ front-end والـ back-end |
| **Rate/resource limit abuse** | تبعت requests وهمية كتير عشان السيرفر يبطّأ نفسه، فيتعمل delay عند السيرفر بدل العميل |

ملاحظة مهمة: لو الـ requests بتتنفذ **بالتتابع** دايماً، غالباً فيه **Session locking** (زي PHP sessions). الحل للاختبار إنك تستخدم **Session tokens مختلفة** لكل request.

### رابعاً: المنهجية: Predict, Probe, Prove

1. **Predict (توقّع):** مش هتختبر كل endpoint. اسأل: هل ده حساس أمنياً؟ وهل فيه احتمال تصادم (أكتر من request بيعدّلوا **نفس السجل**)؟
2. **Probe (استكشف):** خد Benchmark للسلوك الطبيعي (إرسال بالتتابع)، وبعدين ابعت نفس المجموعة بالتوازي وقارن. أي اختلاف هو clue: رد مختلف، إيميل مختلف، تغيير في سلوك التطبيق بعدها.
3. **Prove (أثبت):** فهم اللي بيحصل، شيل الـ requests الزيادة، وتأكد إنك تقدر تكرر النتيجة.

### خامساً: الدروس المستفادة

1. **الكود الصح منطقياً مش كفاية.** الكود اللي بيشتغل تمام مع request واحد ممكن يتكسر مع اتنين.
2. **كل request ممكن يكون "سلسلة خطوات" مخفية**، وفي كل فاصل بين خطوتين فيه Sub-state ممكن يتستغل.
3. **الثغرة مش محصورة في الفلوس والكوبونات.** بتوصل للـ Authentication والـ MFA والـ Password reset.
4. **الحل مش إنك "تتأكد قبل ما تنفذ".** الحل إن الفحص والتنفيذ يبقوا **عملية ذرية واحدة (Atomic)**.
5. **أي طبقة تخزين مش بتحمي طبقة تانية.** مثلاً الـ Session مينفعش تحمي الداتابيز من تجاوز الحدود.
6. **الـ ORMs بتخبّي الـ transactions**، فهي بتاخد المسؤولية عنها. ممكن تكون مصدر مشكلة لو مش فاهمها.

### سادساً: إضافات من عندي

#### 1. إزاي تكتب الكود الصح (مثال عملي)

**الكود الضعيف:**

python

```python
coupon = db.query("SELECT used FROM coupons WHERE code =%s", code)if not coupon.used:    apply_discount(order)    db.execute("UPDATE coupons SET used = true WHERE code =%s", code)
```

**الكود الآمن (Atomic update):**

python

```python
rows = db.execute(    "UPDATE coupons SET used = true WHERE code =%s AND used = false", code)if rows.affected == 1:    apply_discount(order)   # أول واحد بس هيكسبelse:    raise "Coupon already used"
```

الفكرة إن الداتابيز نفسها هي اللي بتضمن إن **واحد بس** يقدر يغيّر `used` من false لـ true.

#### 2. أدوات الحماية الإضافية

- **Unique constraints** في الداتابيز (مثلاً مينفعش نفس المستخدم يستخدم نفس الكوبون مرتين على مستوى الـ schema)
- **`SELECT ... FOR UPDATE`** لقفل الصف (Row-level locking) أثناء الـ transaction
- **Optimistic locking** باستخدام عمود version: لو الـ version اتغير، العملية تفشل
- **Idempotency keys** في الـ APIs بتاعة الدفع، عشان نفس العملية متتنفذش مرتين
- **Distributed locks** (زي Redis lock) في الأنظمة الموزعة، مع الانتباه إنها ليها تعقيداتها الخاصة

#### 3. حوادث حقيقية

ثغرات الـ Race Condition اتاستغلت في الواقع في أنظمة الـ Gift cards والمحافظ الإلكترونية وبرامج الـ Referral وبورصات العملات الرقمية، وكان بيتسحب رصيد أكبر من الموجود. وده سبب إن بعض الشركات بتدفع مكافآت عالية لها في برامج الـ Bug Bounty.

#### 4. نصايح للمطورين

- اعتبر **كل endpoint بيغيّر حالة** (State-changing) قابل للاستدعاء 50 مرة في نفس الثانية.
- اكتب **اختبارات concurrency** في الـ CI: شغّل نفس العملية على threads متوازية وتأكد إن النتيجة صحيحة.
- راقب الـ logs: لو شفت نفس الـ coupon/gift card اتستخدم مرتين في نفس الميلي ثانية، ده مؤشر هجوم.

#### 5. نصايح للي بيتعلم Pentesting

- تدرّب على **PortSwigger Labs** (المذكورة في النص): Limit overrun ثم Rate limits ثم Multi-endpoint ثم Single-endpoint ثم Partial construction.
- اقرأ الـ whitepaper الأصلي *Smashing the state machine*.
- **الاختبار يتم بس على أنظمة مصرّح لك بيها** (Labs أو Bug Bounty بنطاق واضح)، وخصوصاً إن هذا النوع من الهجمات ممكن يسبب خسائر مالية حقيقية أو تلف بيانات لو اتجرّب على نظام إنتاج.

### الخلاصة

الـ Race Conditions مش "bug" عادي، هي **ضعف في تصميم الـ state** بتاع التطبيق. السر في الدفاع إنك تشيل الـ Sub-states من الـ endpoints الحساسة، بجعل العمليات **ذرية (Atomic)** وبالاعتماد على إمكانيات الداتابيز في التحكم بالتزامن، مش على فحوصات في كود التطبيق.
